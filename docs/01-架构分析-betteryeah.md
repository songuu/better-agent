# BetterYeah AI 架构分析

> 证据来源：`ai-docs.betteryeah.com` 全站手册 + 43 篇更新日志 + `www.betteryeah.com` 三个产品页。
> 未登录产品实例，运行时内部实现（调度算法、向量库选型、并发模型）属推断，已标注。
> 读取规则：本文记录竞品观察，不是本项目的最终决策；安全、租户、凭据和恢复语义以 ADR-001 至 ADR-004 为准。

## 1. 产品拓扑

八个一等公民：

```
                    Agent（对话式智能体）
              角色设定 / 技能 / 任务 / 知识 / 数据
                 |           |            |
      工作流 Flow-as-Service  插件 Plugin  知识库 KB / 数据库 DB
                 |           |            |
                 +----- Skill 服务入口（2026-03；Agent 绑定待实证）-----+
                 |
   MCP 服务出口 | 发布渠道（API/SDK/钉钉/飞书/企微/微信） | 效果观测
```

分析判断：Agent 是对话式编排层；Flow 是显式图编排执行层（可包含非确定性的 LLM 节点）；插件是原子工具层，知识库/数据库是状态层，MCP/渠道是出口层。这是本研究的分层语言，不是对竞品内部运行时的实现断言。

2026-03-05 的公开更新资料显示了 Skill 服务/包入口；是否以及如何由 Agent 直接绑定、其版本与运行生命周期尚缺直接证据，不能据此反推“此前 Agent 直接挂工作流/插件”的内部原因。

## 2. Agent 运行时模型

| 构件 | 机制 | 关键细节 |
|---|---|---|
| 角色设定 | 结构化 Prompt | 六段骨架 `# 角色 / # 目标 / # 技能 / # 要求 / # 工作流 / # 输出格式`；结构化模式七主题，每主题可调权重 |
| 技能 | 插件 \| 工作流 \| 子Agent；独立 Skill 服务入口待实证 | 模型自主判断的公开规则以插件/工作流说明书为证；独立 Skill 的 Agent 路由/参数/生命周期不作未证实推断 |
| 任务 | 异步调用技能 | 不阻塞对话，完成后推送；支持定时；预设任务对使用者默认关闭且不可修改 |
| 知识 | 强制查询 \| 按需查询 | 按需模式需「知识库说明书」 |
| 数据库 | 关系型 | 存用户交互历史、交易订单、环境状态变化 |
| 变量 | `{{character}}` | 会话前由使用者填，或 API `inputs` 注入；每次新会话赋值一次 |

公开材料能确认：角色设定、技能说明与输入描述会参与 Agent 的对话与技能选择，且说明书质量会影响调用效果。planner/executor 是否分离、是否存在显式状态机、内部路由/反思实现均未公开；在取得官方契约或受控实验前，不能把它们写成产品事实。

## 3. 工作流引擎

节点清单（手册穷举）：

```
开始(表单 | Webhook) → 输出
LLM · 知识库(QUERY_DATA / INSERT_DATA) · JavaScript&Python(CODE) · API
Flow(子流程) · 逻辑分支 · Plugin · 意图识别 · 文本 · 图文分类器 · Loop循环 · 条件循环
```

- **分支**：JS 条件表达式（`api_1.success === true`），自上而下短路，首个命中即执行且后续不再判断，兜底走最末 Else。跨分支节点不可互访
- **变量引用**：`start.content` 点路径。分支条件里变量不加双花括号——与 Prompt 内插值语法不一致，是易错点
- **LLM 节点**：模型全家桶（ChatGLM3 / Moonshot 8k-128k / 千帆 ERNIE-Bot-4 / GLM-4 / 讯飞 / 混元 / qwen-plus / DeepSeek-R1、V3）；`创造性` = temperature；`上下文` 接受 role/content 数组 JSON；JSON 输出仅 OpenAI 系可用；多模态经上下文传 `image_url` / `video_url`
- **运行方式**：单次 / 批量（Excel 多组入参）/ 定时。定时任务「运行参数是创建时设定的，无法随着时间的推移而动态变化」
- **多环境**：开发→测试→生产，环境变量隔离知识库/子流程/模型，逐级发布不覆盖其他环境。「一旦激活，无法还原为普通Flow」
- **调试**：节点级日志（入参/出参/耗时）；除开始、输出、分支外支持单节点执行
- **集成**：Flow-as-a-Service，每个 Flow 自带 API；Workspace 级 API Key，重新生成后旧 Key 立即失效

## 4. 知识库 / RAG 链路

```
上传(Word/Excel/PPT/PDF/网页/图片/视频)  多模态大模型 + OCR + 声轨识别
  ↓
自动分段  Word类(标题+段落, >500字切) · PPT类(一页一段) · Excel(行+表头)
          通用类(\n\n, >500字切) · QA分段 · JSON分段
  自定义：分段标识符(支持转义字符) + 每段最长字数(建议500)
  ↓
Embedding  双模型(多语种 / 纯中文) + text-embedding-3-large + jina-embedding-V3 + jina-clip-v2
  单段失败仅异常标记，可手动重分段或「AI一键处理」
  ↓
三路查询(可多选组合)
  语义查询  向量相似度，跨语言，弱于精确词与专业术语
  关键词查询 段落维护的关键词精确匹配，无维护则查不到
  全文查询  分词 + 词频权重排序
  + 近义词表
  ↓
结果重排(开箱即用，免部署免第三方 KEY，宣称准确率 +69%)
  ↓
知识匹配最大结果数 → 注入 Agent；无命中则回退训练数据或转调技能
```

架构评价：解析与分段是真功夫（layout 感知、非标准表格、多模态统一入口），是国内 ToB 场景实际痛点。检索侧仍有待补证实的边界：三路查询的融合权重或 RRF 策略、相似度阈值和 parent-child 策略未公开。Flow 知识库节点已公开“属性筛选”（手动、手写 SQL、AI 写 SQL）；但 Agent 编辑页是否支持等价的检索元数据筛选及其执行语义尚未证实。500 字硬上限对长表格与法条类文档偏紧。

## 5. 工具生态

| 层 | 机制 |
|---|---|
| 官方插件 | 40+，含网页解析·Bing/Google搜索·AI识图/生图·小红书/抖音/淘宝抓取·通用文档解析·大文档问答·图表绘制·AI图生视频·HTML转图片·飞书云文档系列 |
| 自定义插件 | 上传 API 文档自动解析生成，或手动搭；另支持 MCP（自定义添加 / 同步第三方 MCP） |
| 插件鉴权 | ① 静态 Service Token / Api Key ② **工作流鉴权**——用一个 Flow 做自定义鉴权，配置入参 + 失效时间，到期平台自动重新鉴权 |
| Skill 服务/包入口 | 公开资料显示可组织工作流、插件和说明；“发布后供 Agent 调用”的绑定与生命周期需取得直接证据后才可写入兼容契约 |
| MCP 出口 | 工作流 / 三类知识库 / 插件均可暴露为 MCP 服务；ID 命名影响 AI 调用成功率 |
| A2A | 自建 Agent 发布为 A2A 服务供他平台对接 |

「工作流鉴权」是聪明设计——用平台自身编排能力解决 OAuth/签名/换 token 这类长尾鉴权，避免为每种鉴权写死适配器。值得直接借鉴。

MCP 方向早期单向（只做 Server），2025-07-31 补上「同步第三方 MCP」后才具备 Client 能力。

## 6. 发布与渠道

```http
POST https://ai-api.betteryeah.com/v1/oapi/agent/chat
Content-Type: application/json
Access-Key: <workspace access key>
Workspace-Id: <workspace id>

{ "robot_id","conversation_id","content","inputs":{},"response_mode":"blocking|streaming" }
```

响应是统一 task 事件流，设计得好：`tool_type` + `status` 双字段即过程透明化的最小充分设计。详见 `06-API契约.md`。

渠道身份映射（`user_type` / `user_id`）：

| 渠道 | user_type | user_id |
|---|---|---|
| 企微机器人 | `WEIXIN_WORK_APP_BOT` | 成员账号 |
| 钉钉机器人 / 流式 | `DINGTALK_ORGAPP_ROBOT` / `DINGTALK_STREAM_ROBOT` | `{senderCorpId}:{senderStaffId}` |
| 飞书机器人 | `FEISHU_APP_BOT` | `{union_id}` |
| 微信客服 / 公众号 / 企微应用 / 钉钉网页 | `WEIXIN_KF` / `WEIXIN_MP` / `WEIXIN_WORK_APP` / `DINGTALK_ORGAPP_WEB` | 暂未支持 |

## 7. 权限模型 —— fail-open 设计缺陷

机制：Workspace 隔离 + 权限变量（`user_type` + `user_id`）+ 企业侧权限回调地址（SPI `action=external_user_auth`），可控资源五类：`agents` / `flows` / `plugins` / `a2a_agents` / `datasets`。

手册两处出现同一句：**「如果没有设置或设置不全，则权限管控不会生效」**，且 `allow` 不填「代表不做任何权限限制」。

这是 fail-open：身份字段缺失时不是拒绝，而是放行全部。结合上表半数渠道拿不到 `user_id`，实际风险是——企业把内部知识库挂到微信客服或企微应用渠道，权限裁剪静默失效，全量知识对外可达。

项目决策：外部兼容面不等于默认风险语义。G0/G1 只采用 fail-closed，不激活 compatibility profile；未来只有独立的版本化 safety envelope、migration 与验收门完成后，才可研究经审批的受限兼容行为，并且仍须完成无 `user_id` 渠道/非 public 资源禁配、发布可见性扫描、审计与缓存失效。详见 [ADR-001](./adr/001-兼容性与安全默认值.md)。

## 8. 可观测与评测

- **Flow 日志**：每次运行的节点明细（入参/出参/耗时），全量留存，可导出、可收藏。**无 token / 成本字段**，耗时是唯一性能指标
- **Agent 日志**：平均首字响应时长 / 平均耗时时长 / 每轮首字响应时长 / 内容输出时长
- **效果观测**（2026-03-05，企业功能）：上传测试集 → 新建自定义评估器（用平台编排能力自己写评估逻辑）→ 自动跑分。评估器输出必须严格符合 `{ "score": 95, "analysis": "", "overall_evaluation": "" }`，「否则会解析不出来结果」
- **效果监控**（2025-01-09）：自定义监控规则 + 自动生成图表 + 模板 + 监控明细与日志；2025-04-17 加高级编排模式（用工作流设计监控指标）
- **数据统计**：整体用量/异常、Agent 用量/异常、工作流用量/异常、知识库积分、应用/知识库明细（分组 + 导出）
- **监控告警**（2024-08-15）：积分余量 / 积分消耗过快 / 应用运行错误 / 应用响应时长超时 / 空间到期；通道为短信、钉钉群机器人（支持 @ 群成员）、电话
- **模型对比**：同一问题跨模型对比；**批量测试集**：跑测试集比对预期答案并给调优建议

用平台自身编排能力实现 LLM-as-judge，架构自洽且省事。缺在线评测——只有离线批跑，无生产流量持续回归、无 A/B、无按 trace 归因。
