## 1. 定位

角色设定 **就是** LLM 的提示指令。手册原话：「'角色设定'就是大模型（LLM）的提示指令，也称为Prompt」。

它不是一个"人设字段"，而是 Agent 的主要角色/约束提示来源。官方材料能确认技能说明、工作流程、输出格式与约束会共同影响对话，但**不能证明**角色设定是唯一的 system prompt 载体，也不能证明内部不存在 router。复刻设计只把它视为可审计的角色提示资产；技能路由仍必须以已发布能力绑定和运行时授权为边界。

## 2. 双轨编写模式

| 模式 | 可见编辑形态 | 编辑体验 | 权重 |
|---|---|---|---|
| 文本模式 | 自由文本编辑区 | 自由书写，全屏，AI 生成/优化 | 无可见主题权重 |
| 结构化模式 | 多个主题卡；每卡可见内容与权重 | 勾选 + 输入生成，并有“一键同步”入口 | **每主题可调权重**，「动态影响Agent对每个主题的执行效果」 |

两模式都配 AI 助手，可一键生成提示词，另有「ai优化」给改进建议。

截图和公开材料只证明两种编辑形态与主题权重；保存载荷、主题 key、文本/结构化互转规则均未公开。若本项目需要双轨互转，可在 §11 采用“文本 source + `{key, content, weight}` 主题数组”的**设计**，并以确认/可回滚的 Draft 操作完成，不能反推为竞品存储结构。

## 3. 官方实证样本对照 —— 段名不统一

四份官方教程的段落结构互不相同，说明**段名是自由的，不是枚举**。手册明确：这些标签「都是根据实际情况可选」，还可自行增加如「#约束」「#禁止」「#注意」。

| 样本 | 模型 / 创造性 | 段落结构 | 挂载 |
|---|---|---|---|
| 手册骨架示例（新闻助手） | — | `# 角色` `# 目标` `# 技能` `# 要求` `# 工作流` `# 输出格式` | 搜索插件 |
| 文档QA助手 | betteryeah-32k / 0.3 | `# 角色` `# 目标` `# 要求` | 仅知识库，无技能 |
| 数据分析助手 | — | `角色` `目标` `要求` `输出格式` | 数据表（Excel 导入） |
| 文章分析助手 | GLM-4 / 0.7 | `Role` `Workflow` `Constraints` `Profile`（英文段名） | Flow「文章阅读器」 |
| 悦享智居案例 | 多模态模型可省插件 | `角色` `技能` `任务` `要求` | 4 个知识库 + 视频/图片问答插件 |

复刻结论：**不要把段名做成枚举校验**。存 markdown 原文 + 可选结构化主题数组，段名自由。

## 4. 段落语义规范

| 段 | 手册原意 | 反模式 |
|---|---|---|
| 角色 / 目标 | 先确定 AI 要做的事——「是解答问题、提供创意、还是执行某项任务？」 | 角色过宽。手册要求「一个Agent尽量充当一个角色」 |
| 技能 | 「告诉大模型，它拥有哪些技能，可以做哪些事情」，可拆技能1/2/3 | 与技能说明书表述矛盾 → 两处打架 |
| 要求 | 「避免使用模糊或双关的词汇」，直接简洁减少误解 | 模糊副词（尽量 / 适当） |
| 工作流 | 按序列出执行步骤（先搜索 → 甄别 → 总结输出） | 步骤与实际挂载技能不对应 |
| 输出格式 | 长度、风格、结构要求，示例「标题：/ 摘要：/ 链接：」 | 只说"美观"不给结构 |

从四份实证样本归纳的高效写法：

| 手法 | 实证原文 |
|---|---|
| 出处约定给**字面格式** | 文档QA助手：`【来自于 文件名 段落】` |
| 排行类问题**指定明细粒度** | 数据分析助手：要求给出 `排行的top10明细` |
| 兜底话术**写进约束段** | 文章分析助手：内容为空时回复"链接安全策略限制、读不到内容，换一个试试" |
| 禁止项**给后果**（压强式） | 悦享智居：「不要对知识库的文字内容进行加工，否则你会受到严重惩罚！！！！」 |
| 负向边界**明确写死** | 文章分析助手：「禁止回答url中不存在的内容」 |
| 路由规则**表格化进「任务」段** | 悦享智居：5 类用户意图 → 4 个知识库 |
| 渲染要求**指定格式载体** | 数据分析助手：`请以markdown表格的形式呈现，确保美观`；文档QA助手：「以图文并茂的方式」 |

## 5. 结构化模式七主题

| 主题 | 交互形式 | 字段 / 行为 |
|---|---|---|
| 角色主题 | 勾选 + 输入 | 【角色信息】【使用场景】【工作任务】【人设性格】【人设语气】【回答长度】 |
| 背景主题 | 输入业务说明 | 生成背景知识 |
| 技能主题 | 有 **【一键同步】** 入口 | 输入名称与描述可自动优化技能 Prompt；同步方向、冲突解决与发布时机未知 |
| 任务主题 | 勾选任务与说明 | 生成执行步骤 |
| 要求主题 | 勾选要求选项 | — |
| 输出格式主题 | 勾选或输入 + 添加示例 | — |
| 自定义主题 | 输入需求内容生成 | 其他主题不够用时自建 |

**技能主题的「一键同步」是可见联动入口**，但截图与当前公开材料都不足以确认其同步方向、冲突策略和生效时机。为避免 §4 的“两处打架”，本项目可选择单向“已建模能力绑定（不含独立 Skill）→ Draft”同步：预览差异、要求确认、可回滚，且同步产物只能回写 Draft；已发布 Release 不能被静默修改。独立 Skill 入口只有在 R-A7 证据闭环后才可纳入该同步范围。这是本项目设计，不是竞品事实。

权重语义：「通过调整每个主题的权重，动态影响Agent对每个主题的执行效果」。手册未公开权重取值范围与实现方式，见 §11 的复刻设计。

## 6. 运行时装配顺序（设计推断）

手册未公开 system prompt 拼装顺序。以下只列出五条公开线索，并在其上定义本项目的安全装配规格；它们不能证明竞品的内部拼装过程。

| 公开线索（非内部实现证明） | 来源 |
|---|---|
| 角色设定被定义为 LLM 提示指令，是角色/约束的一项提示输入；是否为唯一 system prompt 载体未知 | 角色设定页 |
| 技能说明书独立配置、用于帮助模型理解调用时机；其内部载体是 prompt、tool schema 或其他机制未知 | 技能页 |
| 知识库有说明书与强制查询配置；其与技能说明书的内部拼装关系未知 | 知识页 |
| 变量支持 `{{}}` 动态设定；具体插入阶段和覆盖顺序未知 | 变量页 |
| 强制查询被公开描述为每轮优先检索；其完整失败/冲突顺序仍待实验 | 知识页 |

推荐的装配边界如下。它统一的是能力的**发现、绑定与模型可见说明**，不是把所有资源降格为同一种执行器：

```
[1] Agent Release → 角色设定、能力 binding、资源 pin、输入/输出契约、展示策略与**授权策略引用**（不是某次授权结果）
[2] 权限变量/当前主体 → 每次调用按该策略解析 `AuthorizationDecision`；无决策或无 grant 时 fail closed，并将结果快照入 Plan/Run
[3] ResolvedAgentPlan → 已授权的能力描述、变量 schema、强制阶段、预算与类型化重试策略
[4] 角色设定（仅注入经验证的变量；结构化模式按权重渲染）
[5] 按需能力描述 → 供模型选择；知识库可描述为查询能力，数据库仅暴露受限的逻辑操作
[6] 强制知识检索 → 检索结果/引用注入上下文；其他强制调用仅在其类型契约明确允许时成为计划步骤
[7] 会话历史（受子Agent通信方式裁剪）与当前用户输入
```

插件、Flow、子Agent、知识库、数据库以及本项目扩展的 `skill_pack` 可以共享 `CapabilityDescriptor`（名称、说明书、资源 pin、输入契约、可见性、grant），以消除发现与绑定的重复；但执行时必须分派给类型化执行器。知识检索要记录 index generation/命中文档，数据库要实施表/列/行与读写策略，Flow 要调用固定版本，插件只声明 `CredentialRequirement` 并在 Run 解析实际凭据，`skill_pack` 要展开固定成员，子Agent 要约束通信方式、深度、预算和子 Run。Instruction Skill/Agent Strategy 是分离的发布资源，分别指导过程和控制推理，只能引用 ResolvedPlan 已允许的 Binding；BetterYeah 独立 Skill 的兼容绑定仍受 R-A7 阻断，不能由本项目扩展反推。授权与审计随类型而变，不能由一个通用 `ToolSchema` 代替。

## 8. 开场白与开场引导

两个独立字段，均不在 §3 段落体系内（属 Agent 配置而非 prompt 段）。

| 字段 | 文章分析助手实证 | 作用 |
|---|---|---|
| 开场白 | 主动邀请用户丢一个网页链接过来 | 声明输入形态 |
| 开场引导 | 一条知识库文档链接 + "相似度是什么意思？" | 给可点击的示例提问 |

悦享智居案例把「开启开场白做提问引导」列为两处关键微调之一，理由是降低上手成本。

**推荐问题**是第三个独立机制（对话后生成，三种来源：根据回答生成 / 知识库生成 / 对话上下文），不要与开场引导混为一谈。

## 9. 变量插值与作用域

语法双花括号，手册示例 `{{character}}`、`{{background}}`、`{{role}}`。定位原话：「用于做一些动态的设定，允许在外部修改Agent的局部提示词」。

| 赋值通道 | 时机 | 持久化 |
|---|---|---|
| 会话界面填写 | 「每次开始新会话，需要使用者提前输入变量内容」 | 否 |
| API `inputs` | 每次请求 | 否 |
| SDK `mount({agentMetadata})` | 挂载时；Prompt 内 `{{xxx}}`，Flow 内 `betterAI.session.agentInput.xxx` | 否 |
| SDK `saveVariables()` | 显式调用 | **是** |

本项目将权限变量与 Mock 模式变量置于**控制面**，不注入 prompt，分别驱动权限裁剪与技能 Mock。截图只证明这些开关存在；竞品是否同样隔离、权限回调协议、变量保存范围和 Mock 的发布/运行时关系仍须以官方契约或黑盒实验确认。

## 10. Draft、Release、Deployment、ResolvedAgentPlan 与 Run 映射（自定规范）

> 本节是角色与展示配置的研究投影，不是第二套领域契约。术语、类型和运行边界以 [Agent Release v1](./architecture/agent-release-v1与能力装配契约.md)、[Agent Runtime / Strategy ABI v1](./architecture/agent-runtime-strategy-v1.md) 与 [Compiled Capability Closure v1](./architecture/compiled-capability-closure-v1.md) 为准；下方示例不得直接生成 schema。

为避免编辑态、行为发布、展示发布、渠道激活、实时授权和执行记录混在一个 JSON 中，本设计采用六个边界：

- **Agent Draft**：可编辑的 UI 原始值与草稿引用；不直接执行。
- **Agent Release**：只冻结角色规则、变量 schema、Instruction Skill/Strategy pin、能力 binding、资源 pin、说明书/closure hash 和静态上限；不包含开场白等渠道展示内容，也不固化终端用户授权结果。
- **Experience Release**：单独冻结开场白、开场引导、推荐提问、快捷入口和展示策略；展示变更不改变 Agent compiled hash。
- **Deployment revision + active pointer**：revision 固定 Agent/Experience Release、环境、渠道、policy profile 和 credential mapping；active pointer 只在准入事务解析，promotion/rollback 不改已接受 Run。
- **ResolvedAgentPlan**：基于固定 Deployment revision、可信主体、当前 grant、输入校验、传递性 capability closure 和预算解析；只包含本次允许的类型化能力，不能回读“最新草稿”。
- **Run**：持久化 Deployment revision、Release/Plan 标识、授权决策与输入/输出安全引用、步骤、尝试和审计事件；它是执行事实，不是编辑配置副本。

| 配置面 | Draft | Release | ResolvedAgentPlan | Run 与 secure default |
|---|---|---|---|---|
| 结构化规则 / 文本角色设定 | 编辑原文、主题、权重与同步状态。 | 规范化角色资产及其哈希。 | 仅插入已校验变量后的渲染结果/安全引用。 | 记录资产哈希而非秘密；变量缺失、格式不符即拒绝。 |
| 开场白、开场引导、推荐提问 | 编辑的 greeting、guides、推荐来源/文案。 | 进入独立 Experience Release，由 Deployment revision 固定；不进入 Agent Release。 | 可给客户端呈现，不自动获得任何能力。 | 只记录用户实际选择的快捷入口/引导标识（如需审计）；不得把展示文案当授权。 |
| 普通变量 | 声明、默认值、校验规则和提示词占位符。 | 变量 schema、允许的来源与默认值策略。 | 绑定本次 API/会话值并完成校验/插值。 | 敏感值仅保留受控引用或脱敏摘要。 |
| 权限变量 | 回调配置引用与参数映射，不能存原始凭据。 | 固定授权策略引用、回调契约/版本与允许的 capability 范围；不固化某次授权结果。 | 认证后按该策略解析本次 `AuthorizationDecision`，取交集：Release binding ∩ grant ∩ 部署策略，并将决策快照写入 Plan。 | 记录决策 ID/时间/结果摘要；回调失败、超时或空 grant 时不暴露能力。 |
| Mock 模式变量 | 仅测试用途的开关与模拟数据引用。 | 明确是否允许测试环境使用；公开/生产发布默认禁用。 | 仅在已获允许的测试调用中解析；数据库 capability 永远不可 Mock。 | 记录 Mock 已用及数据版本/哈希；不能伪装为真实外部副作用。 |
| 强制调用 / 强制知识检索 | 用户选择的资源与预期顺序。 | 已验证的 binding、资源 pin 与允许的强制语义。 | 编译成显式前置步骤，先经过授权与预算检查；不能仅靠 prompt 文字。 | 每个强制步骤都有 Run step/event；资源不可用或无权时失败而非回退到未授权调用。 |
| Agent 任务 | 草稿的时间、输入与目标选择。 | 仅可固定到 Plugin 或 Flow 的已发布契约；其他类型须先定义新的任务适配器。 | 调度触发时以服务主体重新解析 grant、输入、预算与重试策略。 | 作为异步 Run 持久化；不能因为“任务”绕过发布 pin 或租户授权。 |
| 快捷入口、隐藏技能图示/名称 | UI 入口与展示偏好。 | 发布的客户端展示策略。 | 只影响经授权能力的呈现，不影响内部可审计性。 | 用户可见事件可隐藏过程，但完整脱敏审计仍保留。 |
| 异常自动重试 | 用户的“请求自动重试”意图。 | 允许的最大次数/退避上限，而非无限总开关。 | 按 capability 的副作用、operation key 与幂等证明收窄。 | 数据库写入和其他未知/非幂等写副作用不得由总开关重试；进入 `SIDE_EFFECT_UNKNOWN`/人工处置路径。 |

该表是复刻设计，不是对竞品内部存储的断言。其执行与审计语义应遵从 Flow IR 的资源 pin 和副作用规则，以及 ADR-003 的 RLS/最小 grant、ADR-004 的 Run/Attempt/Step 事实模型。

## 11. 复刻实现设计

```ts
// packages/agent-runtime/src/role-setting.ts
export type RoleSettingMode = 'structured' | 'text';

export interface RoleSetting {
  mode: RoleSettingMode;
  text?: string;                       // text 模式：markdown 原文，段名自由
  themes?: RoleTheme[];                // structured 模式
}

// 单独发布为 Experience Release；不能参与 Agent compiled hash。
export interface ExperienceSetting {
  opening?: { greeting?: string; guides?: OpeningGuide[] };
  recommendedQuestions?: RecommendedQuestionPolicy;
}

export interface RoleTheme {
  key: 'role' | 'background' | 'skill' | 'task' | 'requirement' | 'output' | string;
  title: string;                       // 渲染出的段标题，自由文本
  content: string;
  weight: number;                      // 0-100，默认 50
  fields?: Record<string, string>;     // 角色主题：角色信息/使用场景/工作任务/人设性格/人设语气/回答长度
  syncedFromSkills?: boolean;          // 技能主题「一键同步」标记
}
```

权重实现（手册未公开，自定规格）——三方案取 A+B 组合：

| 方案 | 做法 | 评价 |
|---|---|---|
| A 强调渲染 | weight ≥70 加 `【重要】` 前缀；≥90 追加一次要点复述 | 可解释、可 diff、无需模型支持 ✅ |
| B 位置排序 | 高权重段渲染靠后（利用近端效应），低权重靠前 | 与 A 叠加，零成本 ✅ |
| C 结构化标注 | 权重写成 XML 属性喂模型 | 依赖模型遵循度，不可预测 ❌ |

两模式做的是内容级转换，不是元数据无损序列化：

```
text → structured   按 markdown 一级/二级标题切分，标题作 title，weight 统一 50
structured → text   按 weight 排序（方案 B）→ 渲染 `## {title}` + content（方案 A 前缀）
```

`structured → text → structured` 后应保留每段的 title 与 content；文本没有可靠的 weight 元数据，因此权重必须重置为默认 `50`。编辑器须在转换前后展示预览并要求用户确认。单测只验证标题/内容与明确的默认权重，不得声称原权重无损。

装配器：

```ts
export interface PromptAssembler {
  assemble(input: {
    role: RoleSetting;
    variables: Record<string, unknown>;   // 已按 ResolvedAgentPlan 校验的 {{}} 插值
    capabilities: ModelFacingCapability[]; // 统一描述；不是统一执行器
    forcedContext?: string;               // 强制查询的检索结果
    history: Message[];                   // 受子Agent通信方式裁剪
  }): { system: string; capabilities: ModelFacingCapability[]; messages: Message[] };
}
```

`ModelFacingCapability` 只承载给模型/客户端的名称、说明、输入契约和资源 pin 引用。其后的调用必须由 capability kind 选择知识、数据库、Flow、插件、子Agent 或本项目扩展的 `skill_pack` 执行器；独立 Skill 入口的绑定语义在 R-A7 证实前不进入兼容承诺。装配器不得借由 `ToolSchema` 绕过授权、租户边界、副作用分类或 Run 审计。

## 12. 验收清单

- [ ] 文本模式支持任意段名（英文 `Role/Workflow/Constraints/Profile` 与中文六段均可）
