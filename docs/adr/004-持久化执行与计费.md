# ADR-004：持久化执行与计费

> **状态：已接受（G0-05 Deployment 准入事实已本地验证；G0-06 Run/计费事实层实现中，尚无生产运行能力）**
> **日期：2026-08-24**
> **关联文档：** [技术架构](../04-技术架构.md)、[Agent Release v1](../architecture/agent-release-v1与能力装配契约.md)、[数据模型](../05-数据模型.md)、[API 契约](../06-API契约.md)、[实施计划](../07-实施计划.md)

## 背景

现有架构提出由运行日志和节点检查点支持持久化执行，也提出在执行计划阶段预扣积分；数据模型目前只有包含 JSON 节点日志的 run_logs 和基础 credits_ledger 草图。与此同时，执行面包含 BullMQ 异步消费、节点重试、外部 API/模型调用、SSE 流式输出、定时触发与后续的统计投影。

单个 JSON 运行日志不能回答以下正确性问题：

- 队列重复投递、Worker 崩溃或租约过期后，哪一个尝试有权继续写入运行状态；
- 远程调用已送达但本地超时后，是否可以安全重试；
- SSE 断线后如何按顺序补发，而不是只把实时连接当作事实源；
- 预扣、实际计量、释放和结算如何避免重复扣费或余额透支；
- Human Input/Approval 等待时如何释放 Worker，并在重复点击、权限撤销、过期或进程重启后至多恢复一次；
- ClickHouse、Redis 或在线日志不可用时，恢复和账务是否仍然正确。

本 ADR 规定拟实现的事实模型、状态机和保留边界。G0-06 的 canonical 实施计划是
[`2026-08-26-g0-06-run-fact-layer.md`](../plans/2026-08-26-g0-06-run-fact-layer.md)，可执行 DDL
只能来自 `packages/db/migrations/004_run_billing.{up,down}.sql`。本文和
`docs/database/004-运行与计费.sql` 中尚未被该 migration、自动化测试与 disposable PostgreSQL 16
读回证明的内容仍是设计，不表示对应表、状态、重放、计费或生产能力已经存在。

## 决策

### 1. Postgres 是执行和计费的唯一事务事实源

Postgres 中的运行聚合、尝试、步骤、事件、检查点、可靠投递与积分账务共同构成事实源。Redis/BullMQ 只负责传输与短期协调，ClickHouse 和 OTel 只消费投影，SSE 只是一种可断线的读取通道。

首次实现时，应以独立表或等价的规范化结构表达以下概念；这是一份数据模型决策，不是可直接执行的 DDL：

| 记录 | 责任 | 最低关键内容 |
|---|---|---|
| runs | 一次用户、Webhook、调度或内部触发的持久化执行意图和最终汇总。 | 插入后不可改的 operation/route/key+intent/canonical receipt/principal/Plan/target+dependency+input pins/accepted output schema ref+hash/root billing owner/accepted_at；非终态始终 active 的幂等键、状态、当前尝试、终态原因、持久 terminal event id/sequence 墓碑、不可变 `terminal_billing_pending`、可随对账推进的 `billing_state`/`billing_settled_at`，以及 events/recovery 分离保留期。 |
| run_attempts | 某次 Worker 领取后的实际执行尝试。 | attempt 序号、队列作业标识、租约/栅栏令牌、Worker 身份、开始/结束、失败分类、重试原因。 |
| run_steps | 一个编译后节点在某次运行中的逻辑进度。 | 稳定 step key、节点类型、状态、输入/输出引用、耗时、消耗、可重试与幂等能力。 |
| run_events | 供审计、SSE 重放和状态重建的只追加事件流。 | run 内单调递增 sequence（由锁定 Run 行分配）、事件类型、脱敏负载、发生时间、关联 attempt/step；`runs.last_event_sequence` 保留其 durable 最大 cursor。 |
| run_checkpoints | 可恢复边界的快照。 | 已固定的 flow/agent 版本、变量状态引用、就绪节点/循环计数、最后 sequence、校验哈希、租约代次。 |
| human_gates | Run 需要补充输入或批准 canonical 操作时的持久等待任务。 | run/call/checkpoint、gate 类型、表单/动作 schema、操作 hash、approver policy、状态、过期、claim/decision actor、resume mutation。 |
| outbox | 与状态变更同事务写入、稍后可靠发送的队列通知、SSE 唤醒、Webhook 或统计投影任务。 | 类型、去重键、载荷引用、可投递时间、投递次数、状态和最后错误。 |
| run_parent_links | 一个 durable child Run 与其直接父 Run 的持久关系。 | 目标形状只保存同 Workspace parent/child 与精确 `join+cascade+safe_summary+wait_for_settlement`；当前 004 基线对 child/link 全部 fail closed，只能由后续专属 migration 在同一版本原子启用 child/link/allocation/event/outbox/exactly-one/cascade。 |
| credit_reservations | **仅顶层 billing owner** 在执行开始前建立的预算占用和终态结算依据。 | workspace、billing owner run、估算上限、已占用/已结算/已释放金额、状态、过期时间和原因。 |
| run_budget_allocations | 从父 billing owner 的预留中原子划拨给 child Run 的额度，而不是第二笔 Workspace 预留。 | reservation、parent/child、分配/已用/已释放金额、状态、分配与结算去重键。 |
| credits_ledger | 不可变的已结算积分账本。 | workspace、`billing_owner_run_id`、实际 producer run/step、账务类型、金额、计量明细、去重键、结算后余额或其版本。 |
| run_billing_reconciliations | `NEEDS_ATTENTION` 终态的人工账务处置证据。 | route-level 幂等键/intent hash、不可变 evidence ref+hash、RECONCILIATION ledger、settled/released 数额和 resolved_at；只推进 current billing state，不改终态。 |

run_logs 可保留为用户可见的汇总/兼容读模型，但不能再作为恢复、去重或扣费的唯一来源。大体积输入、输出或模型原始片段可放入对象存储；数据库必须保存其不可变引用、内容哈希、数据分类和保留策略，状态转移仍以 Postgres 记录为准。

### 2. 运行、尝试、步骤与积分采用显式状态机

运行状态机：

~~~
ACCEPTED -> QUEUED -> RUNNING -> SUCCEEDED
                         |         -> FAILED
                         |         -> CANCELLING -> CANCELLED
                         |         -> EXPIRED
                         |         -> NEEDS_ATTENTION
                         |         -> WAITING_FOR_INPUT ─┐
                         |         -> WAITING_FOR_APPROVAL├-> RESUMING -> QUEUED | FAILED | CANCELLED | EXPIRED
                         |                               ┘
                         +-> RETRY_WAIT -> QUEUED
                         +-> RECOVERING -> QUEUED | FAILED | NEEDS_ATTENTION
~~~

- ACCEPTED 表示请求、预算占用和初始 outbox 已在同一事务中持久化；
- RETRY_WAIT 只能由可重试的失败进入，且必须带下一次尝试时间和原因；
- RECOVERING 用于租约过期或 Worker 非正常退出后的检查点恢复；
- WAITING_FOR_INPUT / WAITING_FOR_APPROVAL 只在 checkpoint、HumanGate、Run event 和通知 outbox 已原子提交后进入；它们不持有 Worker lease；
- RESUMING 是一次短事务 claim：校验 mutation 幂等、决策者、过期、原 Plan/operation hash、credential/resource epoch 和预算后投递新 attempt；
- NEEDS_ATTENTION 用于无法确认外部副作用的情况，禁止自动重试；
- SUCCEEDED、FAILED、CANCELLED、EXPIRED 和 NEEDS_ATTENTION 都是终态；人工处置只能追加 resolution/correction/audit，若需再次执行业务操作必须创建新请求与新 Run，不能在原 Run 创建新 attempt。

`runs.status` 逐字使用 Agent/Flow/数据库共享的内部 `RunStatusV1`：`QUEUED|RUNNING|WAITING_FOR_INPUT|WAITING_FOR_APPROVAL|RESUMING|CANCEL_REQUESTED|SUCCEEDED|FAILED|CANCELLED|TIMED_OUT|NEEDS_ATTENTION`。`ACCEPTED|RETRY_WAIT|RECOVERING|CANCELLING|EXPIRED` 只属于内部调度列，并分别折叠为 `QUEUED|CANCEL_REQUESTED|TIMED_OUT`；WAITING、RESUMING 与 NEEDS_ATTENTION 在内部事实层不得再次隐藏或改名。`NEEDS_ATTENTION` 是 `SIDE_EFFECT_UNKNOWN` 的 operator-hold 终态；公开 REST/SSE 使用独立 `PublicRunStatusV1`，将 WAITING 投影为非终态 `RUNNING`，将内部 `NEEDS_ATTENTION` 投影为 `FAILED + SIDE_EFFECT_UNKNOWN + retryable=false + requires_operator_action=true`。对账只能追加 resolution/correction 与推进 current billing state，不能恢复原 Run；公开投影和旧 task adapter 都不能反向成为运行状态真源。

尝试状态机：

~~~
PENDING -> LEASED -> EXECUTING -> SUCCEEDED
                                  -> FAILED
                                  -> TIMED_OUT
                                  -> ABANDONED
                                  -> CANCELLED
                                  -> UNKNOWN
                                  -> SUSPENDED
~~~

UNKNOWN 表示外部操作可能已发生但平台没有收到可信结果，例如请求已发出后连接中断。UNKNOWN 使运行进入 NEEDS_ATTENTION，而不是按普通网络错误重放。SUSPENDED 只表示该 attempt 已成功把 durable gate/checkpoint 交接给等待状态；resume 必须创建新 attempt，不能复活旧租约。

步骤状态机（逐字使用共享 `StepStatusV1`）：

~~~
QUEUED -> RUNNING -> SUCCEEDED | SKIPPED | FAILED | CANCELLED | NEEDS_ATTENTION
                    -> SUSPENDED -> RESUMING -> RUNNING
~~~

`SUSPENDED` 是持久等待态而非终态；`NEEDS_ATTENTION` 是 Step operator-hold 终态。Run finalizer 必须把剩余 `QUEUED` Step 收敛为 `SKIPPED`，并按终止原因把 `RUNNING|SUSPENDED|RESUMING` 收敛为 `SUCCEEDED|FAILED|CANCELLED|NEEDS_ATTENTION`，终态 Run 下不得留活动 Step。

积分预留状态机：

~~~
HELD -> SETTLED
     -> RELEASED
     -> EXPIRED
~~~

预留在准入事务中以锁定的余额/余额版本建立，并立即影响可用余额；实际计量逐步结算，未使用部分释放。不能以“运行结束后再统一扣费”替代预留，也不能允许余额在并发场景下变为负数，除非未来另立 ADR 引入明确的授信能力。

### 2.1 顶层 Run、child Run 与父预留

本 ADR 区分直接被用户、Webhook 或调度接受的 **top-level Run**，与由已接受 Run 异步派生的 durable **child Run**。同一 Run 内的同步嵌套 Flow/能力执行不是 child Run；只有具有独立队列、尝试、取消或恢复生命周期的异步 Flow/SubAgent 才创建 child Run。

下述 child/allocation 是已接受的目标决策，不是当前 004 基线已可执行的路径。由于基线尚未完整实现 allocation、deferred exactly-one link 与 cascade intent/outbox，它固定 `run_kind=top_level + billing_owner_run_id=self`、拒绝所有 parent-link INSERT，并对任何已有 link 的取消路径返回不支持。只有后续专属 migration 在同一发布中建立 child + link + allocation + initial event + dispatch outbox 原子函数、提交前 exactly-one constraint 与父 cancel 可去重 cascade intents/outbox，并通过并发/回滚夹具后，才能放开 child CHECK/触发器。

- top-level Run 是其自身 `billing_owner_run_id`，且只在首次接受事务中建立一笔 Workspace `credit_reservation`；
- child Run 必须先在同一 Workspace 中持久化 `run_parent_link`，其 `billing_owner_run_id` 固定为根 top-level Run。`runs` 持久化不可变 `run_kind` 与该 root owner：top-level 必须 self-owner，任意 child 必须与直接 parent 共享 root owner。child 不得再创建、追加或释放一笔独立的 Workspace 余额预留；
- 创建 child 的事务必须锁定 billing owner 的 `credit_reservation`，同时写入 child Run、parent link、初始 outbox 与 `run_budget_allocation`。任意时点，所有 active child allocation 的剩余额之和必须不大于父预留的 `unconsumed_amount`；不满足时不得投递 child。只有 billing owner 的准入/增量预留规则可增加总预算，child 本身不能绕过父预留从 Workspace 余额另行取款；
- 实际用量以规范化 `agent_charge_attributions` 记录 metered Run/Call/Step 与 allocation，但账本只以 `billing_owner_run_id` 结算一次；attribution 与 ledger/billing owner 的复合 FK、allocation 上限与唯一 charge key 同时成立，重试或重复投递不能再次扣费；
- G0/G1 的持久化 link 只接受 `join + cascade + safe_summary + wait_for_settlement` 的精确组合，父 Run 维持非终态，直至所有 join child 都形成终态且 allocation 已结算或释放。当前 SQL 不保留 `detach`、`do_not_cancel`、`none/structured` 或 `billing_pending` 作为可写 dormant enum。未来若需要 detach，必须以新 schema version、迁移、独立 sealed admission profile 与验收门引入，不能通过隐藏字段、插件或 SubAgent 绕过。
- 父取消必须在同一事务中记录取消意图，并按 G1 唯一固定的 `cancel_propagation=cascade` 向 join child 发出取消。任何 child 的取消、失败、超时或不可确认副作用都必须先结算/释放 allocation，再按已发布的 join 规则影响父 Run 的终态或审计，而不能提前释放仍被 child 占用的父预留。未来 G2 若引入 detach，必须在新 schema version、迁移和独立 sealed gate 中重新定义其取消与终态语义，不能沿用或暗启当前 G1 字段。

因此，“Run 被接受即建立预留”只适用于 top-level billing owner；child 的接受以父预留的原子切分为预算准入条件。这是设计契约，尚未实现任何表、事务或状态。

父子拓扑由数据库约束和唯一受控事务共同保证：parent link 直接拒绝 child 等于 parent；allocate_child_budget 先锁 Workspace 与根 billing owner，再按稳定顺序锁 parent/child/reservation，并递归遍历候选 parent 的祖先链，发现候选 child 即拒绝。因而 root 到 child 到 grandchild 可以成立，但自环和 descendant 指向 ancestor 的环在写 allocation、event、outbox 前失败。

Run 终态也必须形成可长期读取的事实。finalizer 在同一事务先追加唯一 terminal event（由 Run 行锁分配并写入 `runs.last_event_sequence`），再写入最终状态、finished 时间、互斥的 `terminal_result_redacted|terminal_error_redacted`、不可变 `terminal_billing_pending` 和 `terminal_event_id|terminal_event_sequence` 墓碑与必要账务动作；成功结果必须由可信 validator 按准入时冻结的 `accepted_output_schema_ref + hash` 验证，只检查 JSON object 不够。当前 004 基线的 validator 为显式 fail-closed stub，G0 必须以 registry-backed 实现和成功/失败 fixture 原子替换后才允许 `SUCCEEDED`。非成功错误则由 finalizer 从冻结 termination reason 生成 closed `ErrorDetail`，调用者不能自报另一错误码。deferred guard 在首次终态事务要求 cursor/墓碑正好指向 terminal event；后续 event retention 可删除事件行，但 finalizer replay 只比较 Run 上墓碑和终态快照，不再依赖已删除的 event。SSE、GET、blocking 与“已终态时取消”的 200 都从 Run 上该终态快照投影，不得在 Step/Event retention 后重算模型/工具输出；sequence 投影为十进制字符串。

不可变终态快照不表示当前账务永远停在原状态。`runs.billing_state` 是独立、可推进的当前结算投影：`PENDING` 表示仍有 reservation/allocation 或结算工作，`SETTLED` 表示全部结算/释放完成，`NEEDS_ATTENTION` 表示账务无法自动收敛且必须阻止清理；进入 `SETTLED` 时写 `billing_settled_at`，其他状态必须为空。`NEEDS_ATTENTION -> SETTLED` 只能由隔离 reconciliation executor 在单一事务写入幂等 `run_billing_reconciliations`、不可变 evidence ref+hash、`RECONCILIATION` ledger、余额/reservation 投影和 SSE wake outbox 后推进；不得改写 Run 终态、原因、result/error 或 terminal 墓碑。G1 只允许 join，因而 Run 形成业务终态时通常已在同一 finalizer 中得到 `terminal_billing_pending=false` 与 `billing_state=SETTLED`；`SIDE_EFFECT_UNKNOWN` 则先保持 `billing_state=NEEDS_ATTENTION` 直至有证据对账。G2 detach 可先形成 `terminal_billing_pending=true + billing_state=PENDING`，child 后续只推进 `billing_state`/`billing_settled_at`，不得改写 terminal event 或快照。公开 GET Run 返回两者，客户端以当前 `billing_state` 判断最终费用和清理资格。

### 3. 请求、调度、队列和外部调用必须各自幂等

1. **请求幂等。** 服务端为每个 HTTP exchange 生成 UUIDv7 `request_id`；客户端相关值只能以可选 `client_request_id` 存档，不能控制服务端 ID。被接受 Run 持久化首次 `accepted_request_id` 与 canonical `202 Operation` acceptance receipt。写操作可省略 Idempotency-Key（持久化列 nullable）；提供非空 key 时，唯一范围严格为 `(workspace_id, principal_id, fixed_route_template, key)`，`accepted_at + 24h` 是初始重放期的下界而不是自动失效时钟。key 在所有非终态（特别是可能超过 24h 的 WAITING/RESUMING）必须保持 active；终态时单调延长到不早于 `finished_at + 24h`，之后只有受控 retention expiry 函数可停用。`principal_id` 必须由已验证的 transaction context 派生：服务凭据为 `credential:<uuid>`，browser session 为 exchange 固定的 `end_user:<uuid>`；不能使用请求字段中的任意用户/主体字符串。服务端先认证并查询历史记录；命中时先验证调用方仍可读取原 Run，不可读按 `RUN_NOT_FOUND` 处理。随后只以 [SSE 契约 §2.4](../api/SSE与异步操作契约.md#24-intent_hash-的-canonical-编码) 定义的 RFC 8785/JCS stable public `intent_hash` 比较：Chat 为 route、schema 版本、robot/conversation/content/规范化 inputs/response mode，Flow 为 route、规范化 inputs/response mode，取消为**路径模板**、schema 版本、`run_id` 与规范化空 body；不得把 credential binding、已解析目标、Release、授权决策、资源 pin 或 Plan 混入该 hash。相同意图一律返回保存的 canonical `202` receipt，不重算当前目标/Plan 或再次预留；意图不同返回冲突。`blocking` 只允许首次 HTTP exchange 在等待窗口内投影一次 `200` 终态，不能把该临时投影视为幂等事实。只有未命中时才解析并固定目标、授权决策和 Plan，并在同一接受事务保存独立 `accepted_plan_hash`。插入后，operation/route/key+intent/receipt/principal/Plan/target+dependency+input pins/root billing owner/`accepted_at` 全部不可改；唯一可变的幂等字段是受控单调 expiry 扩展和宽限期后停用。这保证 Release 或 binding 之后变化不会改变可读原 Run 的重放结果，也不会让重放创建第二个预留。
2. **调度与 Webhook 幂等。** 定时任务以固定的 schedule fire 标识生成幂等键；Webhook 优先使用来源事件 ID，否则使用受签名时间窗口内的规范化载荷摘要。二者均在接受请求前写入事实源。
3. **队列幂等。** 队列消息只携带 run/attempt 引用及去重信息。Worker 以数据库条件更新领取 LEASED 状态，生成栅栏令牌；任何步骤提交、检查点或终态写入都要验证该令牌，旧 Worker 即使晚到也不能覆盖新尝试。
4. **外部副作用幂等。** 对外 API、插件、模型计量和回调都使用稳定 operation key。只有目标系统明确支持该 key 或节点具有可证明的幂等/补偿语义时，才可自动重试。无法证明安全性的超时必须进入 UNKNOWN/NEEDS_ATTENTION。
5. **账务幂等。** 每笔实际消耗以 run、step 和计量事件组成唯一去重键；重试同一节点不得产生第二条已结算账务。图文分类器等零积分节点仍可记录零消耗事件，但不应产生可用余额变动。
6. **Human Gate 恢复幂等。** `resume(gate_id, mutation_id, decision)` 使用独立 mutation record；唯一范围与取消一致，为 Workspace、经认证 actor、固定 resume 路径模板和 key，**不包含**目标 Run/Gate。规范化 `run_id`、`gate_id`、`action` 与 `input` 放入 JCS intent；因此同一 key 跨目标复用必然冲突。claim 只允许 `PENDING` Gate 原子转移一次；相同 mutation 重放首次结果，不同 actor/decision/hash 冲突。mutation identity/intent/receipt 不可改写，键在目标 Run 全生命周期（含长期 WAITING）active，目标终态后再保留至少 24h；批准绑定待执行操作 canonical hash，不等价于通用 grant。

Run 创建和 Run 变更使用不同的幂等事实源。创建请求记录在 runs；取消与 Human Gate resume 记录在独立 mutation idempotency 表，其唯一范围为 workspace、从认证 context 派生的 principal、固定 route template 和 key，**不包含 target**，并保存含目标 Run/Gate 的 JCS intent hash、首次安全响应投影、event sequence 与单调重放期下界。该时间到达不会在目标非终态时停用 key；只有 retention owner 的受控函数可在目标终态且 24h 宽限已过后停用，所有 expiry 变更只能单调延长。mutation 函数不接受 principal 或 opaque intent hash 参数：取消的固定 scalar-only JCS preimage 由可信 SQL `cancel_intent_hash_v1(run_id)` 逐字构造并哈希，命中时仍独立比较保存的 `target_run_id` 与本次 `run_id`，任一不同都返回 409；通用 JSON/JCS 必须在经版本锁定的可信 canonicalizer 中完成，数据库不得用 `jsonb::text` 冒充 RFC 8785。函数在比较前调用同一已认证主体的 Run/Gate access gate；相同 intent 只重放保存响应。取消可沿用公共写操作规则：缺 key 时不承诺网络重放去重；Human Gate resume 则必须携带非空 key，缺失直接以 400 拒绝，首次成功与重放均返回保存的 202 响应。

### 4. 可靠恢复与 Worker 重试

top-level Run 的一次接收事务至少包含：创建 run、创建或确认 credit_reservation、写入初始 run_event，以及写入启动 outbox。目标 child 接收事务必须同时创建 child run、锁定并原子写入父 link/预算 allocation、写入初始 run_event 和启动 outbox，且不得创建独立 credit_reservation。当前 004 基线未具备这个原子函数，因此对 child/link 插入显式 fail closed；不能以多步应用写入模拟。任一部分失败时，请求不得被标记为已接受或已派生。

Worker 只能在持有有效租约和栅栏令牌时推进运行。它应在节点边界持久化步骤结果和检查点，再通过 outbox 通知下一步；不能把内存中的变量、Redis 锁或 BullMQ 作业体当作唯一恢复资料。检查点必须绑定已发布的 Flow/Agent 版本，保存可恢复的变量和调度游标，并排除原始密钥；敏感值仅保存受控引用或脱敏摘要。

进入 Human Gate 时，candidate Worker 必须先在同一个 Run/barrier CAS 事务建立 `DRAINING` barrier、冻结全图新调度和 frontier、提交 checkpoint，并将自己的可执行 lease 原子标记为 `RELINQUISHED`、handoff 给不能执行业务动作的 host-only barrier owner；任一步失败整体回滚。host drain/checkpoint sibling，证明 active executable lease、待 dispatch outbox 和未对账 attempt 全部为零后，才在匹配同一 owner generation 的 waiting 事务递增 execution fence、提交 Step=`SUSPENDED`、pending gate、Run=`WAITING_FOR_INPUT|WAITING_FOR_APPROVAL`、`run.waiting` event 与通知 outbox，并释放 barrier owner。candidate lease 不能等到 WAITING 后再释放，barrier owner 也不计入 executable lease。普通恢复器不得领取 WAITING Run；只有最后一个正向 Gate decision 的受控 resume claim 在重新授权通过后将 Run 与 Step 转入 RESUMING、创建新 PENDING attempt 并投递 outbox；中间正向 decision 只物化下一 Gate，reject/expire 只提交终态意图并唤醒唯一 finalizer。WAITING 无论持续多久都不会因初始 24h 重放期下界而停用 Run/mutation key 或清理 gate/checkpoint。取消、过期和拒绝也必须通过锁定 Gate/Run/barrier 的单一胜者事务形成唯一状态与事件。

租约到期时，恢复器先确认旧尝试不再拥有有效栅栏令牌，再基于最后成功检查点创建恢复尝试。重复消息、重复调度器或重复 outbox 投递是预期情况，接收端需要按去重键处理。超出节点/运行重试上限、被取消或预算无法追加时，必须形成明确终态和审计事件。

### 5. SSE 是按序可重放的投影，不是实时连接的副本

每个对外可见事件在分发前写入 run_events，并由锁定 Run 行的受控 append trigger 分配 run 内单调递增 sequence；调用方不允许自行指定 cursor。`ba_runtime` 没有原始 event INSERT，普通进度只能经 allowlist append function；取消、terminal、credit 和 outbox 事实专属受控 billing/finalizer 路径。任何供低权执行角色调用的 `SECURITY DEFINER` 函数必须将 `pg_temp` 显式置于固定 `search_path` 的末位，并以 schema-qualified 名称访问持久 relation，避免临时表遮蔽认证、保留或账务闸门。SSE `id` **就是**该 sequence 的十进制字符串；`run_id` 已由事件订阅 URL 绑定，禁止拼接成 `run_id + sequence`。`runs.last_event_sequence` 是 retention 后仍保留的权威最大 cursor，`run_events` 可另有 UUID `event_id` 作为不可变记录身份，但它不是 SSE cursor。客户端以 Last-Event-ID 或等价的 after sequence 请求重放，按 `(run_id, sequence)` 去重，因为断线临界点允许至少一次发送。

终态时同步保存 `terminal_event_id + terminal_event_sequence`墓碑。它们与 `last_event_sequence` 在终态后均不可改，使 terminal replay 在 run_events 已过 7 天窗口并删除后仍可比较原 event ID/sequence 而不创建新 terminal intent。

现有对等目标要求的 task 事件和逐字符 llm_response 可映射到该事件流，但实现不能只保存在连接内存中。事件载荷不得包含密钥；超大文本须以受控载荷引用或分块记录，并保证重放顺序可恢复。

当请求的位置早于可重放窗口时，服务端必须返回 `410 EVENT_CURSOR_EXPIRED`，并在错误 `data` 中给出 `run_id`、`min_sequence`、`last_sequence`、`operation_url` 与 `events_url`，以便客户端读取运行汇总后重新订阅；`last_sequence` 永远来自 durable Run cursor，全量 event retention 后 `min_sequence=last_sequence+1`。该错误是通用 `data: null` 错误 envelope 的显式例外，机器可读 schema 以 API 契约为准。

### 6. 账务与分析投影分离

模型、工具和多模态节点把可审计的计量明细写入 Postgres 账务事务。top-level Run 的直接用量从自身 reservation 结算；child Run 的用量先扣减其 allocation，再以根 `billing_owner_run_id` 只写入一次账本。若实际成本低于预留，则在所有 direct/child allocation 结算后释放余量；若成本会超过总预留，则必须由 billing owner 在发起额外有成本操作前取得增量预留，否则停止并按余额不足处理。对于 G1 唯一允许的 join child，billing owner 只有在所有 child allocation 结算/释放后才可完成 reservation 的最终结算并进入终态。每次账务动作必须同步推进可审计的 `billing_state`，且只有 `SETTLED` 才能写 `billing_settled_at`。credits_ledger 是不可变账本，workspaces 的余额字段只能是受事务约束的当前余额投影，不能反过来重建账务事实。

数据库角色按 `ba_admission_executor`、`ba_execution_executor`、`ba_metering_executor`、`ba_finalizer_executor` 阶段分离。execution mutation 必须在每次写入时验证当前、完整且未过期的 Run/Attempt/Step、`session_user=lease_owner`、lease token 与 fencing tuple；但 metering/finalizer 不再要求消费时旧 Worker lease 仍为 current。execution owner 只能在该 lease 有效时原子建立 immutable usage/termination producer attribution，封存当时的 Workspace、billing-owner/metered Run、reservation、Attempt/Step、producer session user、token/fence/expiry、DB authorization time 与 operation/effect hash。cross-phase consumer 在 Workspace 账务锁之后锁定该来源，验证历史 tuple 和 operation-specific CAS，即使旧 lease 此后已过期或被 fence，也只能 exactly-once 消费 exact source；consumer login 不得冒充 producer owner。消费事务同时写入 run-owned、append-only、不可被技术 retention 删除的 billing authority receipt，再进入共享账务 kernel。缺失、篡改、混合、已被不同 operation 消费的来源一律在资金移动前拒绝。

`billing-intent/1` 与 `credit-ledger-entry/1` 保持原有 current-fence 兼容语义；protocol-v5 使用新的 `/2` authority union：`USAGE_ATTRIBUTION` 只能结算，`TERMINATION_ATTRIBUTION` 只能释放，pre-claim durable cancellation 只能由已认证的 `CANCEL_REQUESTED + RUN_CANCEL_REQUESTED` durable fact 派生 `CANCELLATION_RELEASE`，不得伪造 Attempt/fence。三类来源遵循无环单向绑定：domain-separated JCS source preimage → `source_authority_hash`/`charge_attribution_hash` → DB 派生 stable charge key → 不含 receipt/ledger ID 的 BillingIntent hash → authority receipt 与 ledger；消费 generation、receipt/ledger ID、whole-record hash和其他 downstream 字段不能回流到 source preimage。`/2` fencing 仍限制为 canonical decimal string `1..9007199254740991`。zero-credit `HELD` cancellation 允许写零 delta RELEASE 并关闭 reservation，但不递增余额版本；已被 confirmed usage 全额闭合的 reservation 不再制造第二条 release。HOLD/`SIDE_EFFECT_UNKNOWN` 分支不消费账务来源、不写 authority receipt、不移动资金，只把 current billing state 收敛为 `NEEDS_ATTENTION` 等待独立对账。

普通 `ba_runtime` 对 reserve/settle/release/finalizer 全部无 EXECUTE，各 phase executor 无原始表 DML、互不继承；对应 NOLOGIN owner 只持有函数所需列权限。finalizer 必须在同一外层事务按 Workspace → Run → Attempt/Step/effect → `RUN_DISPATCH` → reservation/allocation → authority/ledger 的锁序清除或 fence 所有活动执行权，退役未投递的 initial `RUN_DISPATCH`，再收敛 Step、唯一 terminal event、Run tombstone/snapshot、账务与 SSE outbox。Gate reject/expire 等无 Worker lease 的入口必须取得绑定 durable source 的 transaction-scoped finalizer claim，不能用空 lease或 caller reason 绕过；004 基线尚无可验证的 GateSpec disposition 关系，因此对 `HUMAN_REJECTED|HUMAN_GATE_EXPIRED` 直接 fail-closed。join child 一旦处于 `NEEDS_ATTENTION`，父 Run 也只能以相同 operator-hold 终态收敛。后续对账只能推进 current billing state，不改写 Run 终态或历史快照。

上述阶段 executor 均不得用客户或外部 API credential 建立工作区上下文。每个阶段只接受受信部署控制面签发、最长 15 分钟、绑定 `workspace + session_user + exact phase` 的 internal service attestation；同一仍有效的 raw attestation 可由相同绑定 login 在新事务或连接重新验真并建立新的 transaction proof，但旧 proof 不得跨事务/连接复制，wrong-phase/login/Workspace/verifier、过期或撤销 token 均无 RLS context。`ba_reconciliation_executor` 只能调用幂等 `reconcile_needs_attention_billing`，没有原始表 DML 或 finalizer 权限。

ClickHouse、OTel 和报表通过 outbox 消费投影。它们的延迟、丢失或重建不得改变 run 的终态、可用余额或已结算账务。运营统计可与账本对账，但不能替代账本。

### 7. 保留期与清理规则

以下为首期默认保留基线；部署方可在不缩短安全与合同要求的前提下延长：

| 数据 | 默认保留 | 规则 |
|---|---|---|
| 活跃 run 及其创建/mutation 幂等键、attempt、step、checkpoint、human gate、parent link、未发送 outbox、未结算 reservation/allocation | 直到形成可审计终态且 `billing_state=SETTLED` | 任何 WAITING/RESUMING、未决、恢复中或当前 billing state 不是 SETTLED 的记录禁止自动清理；内部终态 NEEDS_ATTENTION 只在已追加幂等 reconciliation evidence+ledger 并推进 billing state 后取得清理资格。初始 24h 重放期下界到达不改变此规则。 |
| 用户可见运行汇总、步骤摘要和 run_logs 读模型 | 终态后 90 天 | 与现有“运行日志 90 天”规划一致；敏感字段应先脱敏或改存受控载荷引用。 |
| SSE 可重放 run_events | 终态后至少 7 天 | 保证有限窗口内的断线续传；窗口外必须显式降级到运行汇总。 |
| 终态后的 checkpoint/human gate、已发送 outbox 去重记录、请求/取消/resume 幂等记录 | 至少 30 天，且不得短于 `finished_at + 24h`、相关重试/审批链接窗口 | 清理前必须确认没有挂起恢复、重投或相同业务去重需求；只有受控 retention expiry 可停用键。 |
| 已结算 credits_ledger 与结算关联 reservation | 不自动按技术日志策略删除 | 最终年限由合同、财务和合规要求确认；账务不能随运行日志 90 天清理。 |
| ClickHouse 统计投影 | 可长期保存，但仅限脱敏/汇总数据 | 现有规划的“统计永久”不得包含可直接还原用户敏感输入、输出或密钥的数据。 |

技术 purge 不得把调用者传入的 archive ref/hash 当作自证。它必须在删除前读取并精确匹配一条由独立归档管道事先建立、不可修改、状态为 VERIFIED 且 APPROVED 并带 verification/approval receipt ref+hash 的 manifest；manifest 缺失、Run/工作区不符、ref/hash 不同或已有同 material kind purge receipt 均 fail-closed。事件清理只在 `events_retention_until >= finished_at+7d` 到达后删除 run_events，checkpoint/outbox 仍保留；恢复材料清理还必须等待 `recovery_retention_until >= finished_at+30d` 与更长的 policy horizon。两类 purge 都必须先证明 `billing_state=SETTLED`；NEEDS_ATTENTION 还必须存在不可变 reconciliation 证据。独立 `ba_archive_evidence_executor` 只有 registration 函数 EXECUTE，无 manifest DML 或 purge EXECUTE；`ba_retention_executor` 只有 purge EXECUTE，无 registration/表权限，两组 NOLOGIN owner/执行角色不得互相继承。成功清理后按 `EVENTS|RECOVERY` 分别追加 purge receipt；任何路径都不删除 `credits_ledger`。`release_credits(..., p_mark_expired=true)` 也必须在锁定 reservation 时读回 `expires_at`，当前时间早于它时拒绝提前 EXPIRED。

## 备选方案

| 方案 | 结论 | 原因 |
|---|---|---|
| 只保留 run_logs JSON，靠其恢复与扣费 | 不采用 | 无法安全表达并发尝试、租约、幂等、检查点、事件顺序和账务状态。 |
| 认为 BullMQ 的一次消费等于端到端 exactly-once | 不采用 | Worker 崩溃、网络超时和外部服务副作用天然会产生至少一次投递与不确定结果。 |
| 只在运行结束时一次性扣费 | 不采用 | 长运行和并发请求会造成余额透支，失败/重试还会掩盖实际消耗。 |
| 只向已连接的 SSE 客户端推送，不持久化事件 | 不采用 | 断线、扩缩容和回放都无法保证顺序与可见性。 |
| 以 ClickHouse 或监控指标作为积分事实源 | 不采用 | 分析系统的延迟和重放语义不适合事务账务。 |
| 引入 Temporal 作为首期恢复引擎 | 不采用 | 当前私有化目标明确避免额外独立集群；先用 Postgres 事务事实源和队列实现可验证恢复。 |

## 后果

正面后果：

- 运行恢复、队列重复、SSE 断线和积分结算拥有明确的可测试语义；
- 执行正确性不依赖 Redis、ClickHouse 或某一台 Worker 的内存；
- 人工等待不占用 Worker，决策、过期、取消和恢复具有与 Run 相同的持久化、幂等和审计边界；
- 对无法确认的外部副作用诚实地进入共享 terminal `NEEDS_ATTENTION`，避免“看似失败、实际已执行”的自动重放；
- 后续可从规范化事实表生成用户日志、统计、账单和审计视图。

代价与约束：

- P0/P1 需要补充迁移、事务封装、租约恢复器、outbox dispatcher、归档任务和高风险并发测试；
- API 契约需要增加 Idempotency-Key、取消/状态读取、SSE 重放和窗口过期语义；
- 流式 token 事件可能带来较大存储量，需以容量测试确定分块、归档和对象存储策略；
- 现有 run_logs 表和 credits_ledger 草图必须在实现前与本 ADR 对齐，不能边实现边默认为 JSON 即事实源。

## 验收

以下为该决策实现时的验收条件，不代表已经通过：

1. 并发提交相同 Idempotency-Key、相同稳定 `intent_hash` 的 top-level 请求仅产生一个 run、一个预算预留、一份 canonical `202` acceptance receipt 和一组初始 outbox 记录；重放先验证原 Run 可读性，随后总是返回该 202 receipt（使用新的 exchange `request_id`），不重新解析 Release/Plan；同键不同意图被拒绝。首次 blocking 连接即使曾在等待窗口内得到 200，也不改变该重放语义。
2. 在 Worker 分别于领取后、外部调用前后、节点结果提交前后崩溃的故障注入测试中，恢复结果符合检查点与栅栏令牌语义，旧尝试无法覆盖新尝试。
3. 队列重复投递和 outbox 至少一次投递不会导致同一可幂等步骤、回调或账务条目重复执行。
4. 不支持外部 operation key 的非幂等节点在“请求已发出但结果未知”时 Attempt 进入 UNKNOWN，内部 Step/Run 进入共享 terminal `NEEDS_ATTENTION`，系统不自动重放；公开 REST/SSE 投影为 `FAILED + SIDE_EFFECT_UNKNOWN + retryable=false + requires_operator_action=true`。
5. 客户端在任意 SSE 事件后断线，使用最后的 run 内 `sequence`（SSE `id`）可以按序补齐；边界重复可由 `(run_id, sequence)` 去重；过期窗口返回已定义的降级结果。
6. 余额不足时，top-level 运行不会被接受；预留、增量预留、实际结算和释放在并发情况下满足余额不为负和账本去重约束。当前 004 基线对 `run_kind=child` 和 parent-link INSERT 全部 fail closed，任何多步应用写都不能留下半成品。后续专属 child migration 必须在同一事务创建 child、link、allocation、初始 event 与 dispatch outbox，并以 deferred exactly-one 约束和并发夹具证明多个 child allocation 不超出父预留、child 不创建第二笔 Workspace 预留；只有该 migration 的 G1 gate 通过后，才验收 `join+cascade+safe_summary+wait_for_settlement` 与 root → child → grandchild。detach、do_not_cancel、none/structured projection 与 billing_pending link 始终不能在 G1 写入；未来启用 detach 前必须另立 schema/migration/sealed gate。
7. ClickHouse、OTel 或 Redis 临时不可用时，Postgres 中的运行终态、账务余额和待投递 outbox 仍可被恢复或重新投影。
8. 清理任务不会删除活跃/未决记录、`billing_state <> SETTLED` 的 Run 或仍在重试窗口内的幂等记录；超过 24h 的 WAITING Run 及其取消/resume key 仍 active，终态后至少 24h 内仍可重放。自动化边界测试分别证明 events 在 `events_retention_until`（G1 下界为 `finished_at + 7d`）前不可删、event purge 不删除 checkpoint/outbox、recovery material 在 `recovery_retention_until`（下界为 `finished_at + 30d`）和更长 `retention_until` policy horizon 到达前不可删。若合同要求延长原始事件窗口，必须显式延长 `events_retention_until`，不得借 recovery horizon 隐式改变 EVENTS purge 语义。
9. 同一 `Idempotency-Key` 的重复取消，以可信 SQL 的固定 `/v1/oapi/runs/{run_id}/cancel` 路径模板、`intent/1`、规范 UUID `run_id` 和 `{}` body 得到同一 intent hash；函数不接受调用方 opaque hash。实际 URL、host、query 或实现语言 serializer 差异不得再产生第二条 `run.cancel_requested` 事件；同 key 即使伪造相同 hash 指向另一 Run，也因独立 target 比较得到 409。

10. 当前基线中，直接写 child、parent link 或对带 link Run 取消都必须以 `0A000` fail closed，且不留下 allocation、event 或 outbox。后续专属 migration 原子启用后，root 到 child 到 grandchild 的夹具才必须成功；child 等于 parent、descendant 指向 ancestor、缺 link/allocation/event/outbox 的提交必须在同一受控事务失败，父取消须写可去重 child intents/outbox，且任一失败不留下部分事实。
11. G1 的所有普通/join 终态（包括内部 `SIDE_EFFECT_UNKNOWN`）固定 `terminal_billing_pending=false`；正常终态的当前 `billing_state=SETTLED`，未知副作用固定内部 terminal `NEEDS_ATTENTION + billing_state=NEEDS_ATTENTION` 并阻止清理，对账只推进 current billing state。GET/SSE 把内部 operator-hold 投影为公开 `FAILED + SIDE_EFFECT_UNKNOWN`，并另行返回 current billing state。未来 detach 只能在独立 schema/migration/sealed gate 后增加 true 快照测试。
12. keyed 取消的相同 JCS intent 必须重放保存的首次 200/202 响应且不新增事件；同 key 的不同 Run（包括调用方声称相同 hash）因 target 独立比较必须为 409，历史目标不可读时为不泄漏存在性的 404。
13. Worker 在 Human Gate 等待期间重启或队列重复投递不能越过 gate；同一 Gate 的并发 approve/reject/cancel 只有一个事务胜出，相同 resume mutation 重放首次结果且不重复副作用。
14. resume 继续固定原 Deployment/Release/Plan/operation hash，但重新校验 actor、过期、credential/resource epoch 和预算；参数变化或权限撤销必须拒绝旧批准，不能解析 latest 或扩大能力。
15. 插入 Run 后，operation/route/idempotency key+intent/canonical receipt/principal/Plan/target pins/dependencies/input/billing owner/accepted_at 任一列的 UPDATE 都失败；直接缩短 expiry、非 retention 延长或非终态停用均失败。mutation identity/intent/receipt 同样不可改，仅受控 expiry 单调扩展/停用通过。
16. `reserve_credits` 的 accepted Plan 不匹配或非 acceptance miss 被拒绝；`settle_credits`/`release_credits` 的 Run、Attempt、lease token、fence、Step/charge attribution 任一不匹配均在资金移动前拒绝。`release_credits(..., p_mark_expired=true)` 在 reservation `expires_at` 前拒绝且不改变余额、reservation、Run 或 ledger；到期后只有绑定 finalizer attempt/fence 的全量未消耗额才能写唯一 RELEASE/EXPIRED 事实。`ba_runtime` 及错误阶段 executor 调用这些函数全部 permission denied。
17. purge 对调用者自带但事先不存在的 manifest、错误 workspace/Run/manifest ID、ref/hash 不匹配、缺少 VERIFIED/APPROVED receipt、`billing_state <> SETTLED`、NEEDS_ATTENTION 缺 reconciliation evidence 或同 material kind 重复 purge 全部失败且不删数据；retention executor 不能插入/改写 manifest。EVENTS purge 只删事件并追加 EVENTS receipt；RECOVERY purge 只删允许的 checkpoint/event/outbox 技术材料并追加 RECOVERY receipt；两者均保持 terminal tombstone 和 `credits_ledger` 行数不变。
18. `finalize_run` 对空/旧/过期 lease、错误 fence、未结算 join child、HELD reservation、错误 termination-reason/status 映射与重复不同 terminal intent 均 fail-closed；`SUCCEEDED` 必须按准入冻结的 schema ref/hash 经可信 registry validator 验证，当前 fail-closed stub 在 validator migration 前不得接受成功终态。成功事务只产生一个 RUN_FINISHED、一个 immutable Run terminal snapshot/tombstone、一个 SSE wake outbox，并且没有 `QUEUED|RUNNING|SUSPENDED|RESUMING` Step；event purge 后同 terminal intent 仍从 Run tombstone 重放，不同 intent 仍冲突。004 基线调用 `HUMAN_REJECTED|HUMAN_GATE_EXPIRED` 必须得到 fail-closed；Gate migration 加入不可变 disposition 证据后，另以 fail/cancel 映射夹具和 `SIDE_EFFECT_UNKNOWN` 优先级夹具验收。
19. 相同 reconciliation idempotency key + intent 只产生一条 evidence、一条 `RECONCILIATION` ledger 和一次余额/reservation/current billing state 推进；不同 intent 冲突。该事务只能把 terminal `NEEDS_ATTENTION` 的 `billing_state` 推进到 `SETTLED`，不得改写 status、termination reason、result/error 或 terminal event tombstone。
