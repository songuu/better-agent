# ADR-003：多租户隔离与凭据模型

- 状态：已接受（文档级架构决策；尚未实现，真实证据待 G0）
- 日期：2026-08-24
- 决策范围：Postgres 租户边界、异步传播、跨表引用、外部和内部凭据
- 关联：[技术架构](../04-技术架构.md)、[数据模型](../05-数据模型.md)、[API 契约](../06-API契约.md)、[实施计划](../07-实施计划.md)、[ADR-001](./001-兼容性与安全默认值.md)

## 背景

早期数据草图虽提出“所有业务表带 `workspace_id`”，但曾依赖调用方设置连接级 `app.workspace_id`；技术栈也选择了 Postgres RLS，P0 的验收目标包含跨 Workspace 越权测试。然而当前草图中许多租户子表仅通过父表间接关联，例如 `agent_skills`、`flow_versions`、`kb_files`、`messages`、`custom_plugin_tools`、`mcp_service_tools`，部分表的 `workspace_id` 还允许为空。单列外键如 `agent_id references agents` 也不能阻止同一工作空间中的记录指向另一工作空间的父资源。

现有 `workspaces.access_key` 被设计为明文且是 Workspace 级万能密钥；它同时出现在 REST 请求头、Web SDK 配置、Webhook URL、MCP 配置和权限 SPI 出站请求中。这会让浏览器泄露、URL 日志、渠道配置导出或任一第三方回调泄露扩大成整个工作空间的控制面与数据面访问。

需要在写第一份迁移和鉴权中间件前，冻结“如何把租户上下文放进每一次数据访问”以及“凭据能访问什么、保存什么、出现在哪里”。

## 决策

### 1. 租户所有权必须是直接、不可空且可由数据库验证的

除明确标记为全局只读的系统目录（例如官方插件目录）外，每张包含客户业务数据、运行数据、配置、引用、凭据元数据、审计、搜索索引映射或队列状态的表，都必须有：

- `workspace_id uuid not null`；
- 到 `workspaces(id)` 的外键；
- `unique (workspace_id, id)` 或等效候选键，以供复合外键引用；
- RLS policy、适当索引以及 `workspace_id` 包含在唯一约束和幂等键中。

仅由父表“可推导”出工作空间不足以构成隔离边界。现有草图中的 `batch_debug_sets.workspace_id` 必须改为 `not null`；子表、会话/消息、版本、关联表和日志均须补齐直接租户列。全局目录不得承载客户密钥、客户私有配置或客户运行数据；其与租户资源的关联表仍是租户表。

租户内父子关系使用复合引用，而不是仅引用全局 `id`。模式示例：

```sql
alter table agents
  add constraint agents_workspace_id_id_key unique (workspace_id, id);

create table agent_skills (
  id uuid primary key,
  workspace_id uuid not null references workspaces(id),
  agent_id uuid not null,
  -- 其余字段略
  foreign key (workspace_id, agent_id)
    references agents(workspace_id, id)
);
```

`flows → flow_versions / flow_env_vars / flow_schedules`、`knowledge_bases → kb_files → kb_chunks`、`conversations → messages / session_store`、`custom_plugins → custom_plugin_tools`、`mcp_services → mcp_service_tools` 以及评测、监控、积分、运行等关系均遵循此规则。

多态 `target_type + target_id`、JSON 内资源 ID 或跨域引用不能被普通外键安全地覆盖。授权、执行或计费依赖这些引用时，必须改为按类型拆分的关联表，或使用数据库约束触发器验证目标的 `workspace_id`；不得仅依赖应用层约定。唯一受控例外是 `published_resource_versions`：它只登记顶层 Agent/Flow/System 的不可变版本，并由 `(workspace_id, published_resource_version_id)` 复合 FK 被 visibility/grant/Run 引用。任何无法在写入时证明同租户的关系不得进入可执行/已发布状态。

### 2. RLS 是运行时最后一道边界，租户上下文只在事务内传播

业务数据库运行账号不得拥有 `BYPASSRLS`，不得以表所有者身份执行普通业务查询。每张租户表均必须：

```sql
alter table <tenant_table> enable row level security;
alter table <tenant_table> force row level security;

create policy <tenant_table>_tenant_isolation on <tenant_table>
  using (
    workspace_id = app.current_workspace_id()
  )
  with check (
    workspace_id = app.current_workspace_id()
  );
```

`app.current_workspace_id()` 只接受受限认证函数在当前事务内建立的签名 `app.tenant_context`，且只存在三条互不混用的来源：外部运行时 API credential、可信管理会话 attestation，或受信部署控制面签发的短时、单阶段 internal service attestation。它忽略调用方可伪造的 `app.workspace_id` GUC。认证 proof 缺失、过期、撤销、wrong-phase、跨 `session_user`、跨管理主体或跨 transaction 时 helper 返回 `NULL`，RLS 不返回或写入任何租户行。政策不得为“上下文为空则放行”设置 fallback。迁移、备份恢复等确需跨租户的管理操作使用独立、最小权限的维护角色，不得复用应用连接池账号。

一次 HTTP 请求、SSE 生命周期中的每个数据库工作单元、Worker job、定时任务和重试均按以下顺序运行：

1. 在同一连接上 `BEGIN`，在任何业务表访问前调用受限的凭据验证投影或可信用户会话 attestation 函数；不得先信任 `Workspace-Id` header、请求 body、队列 payload 或客户端写入的 GUC。
2. 认证函数验证调用者并建立本事务的签名 `app.tenant_context`；随后才可通过 RLS 读取 scope、成员资格和资源授权。
3. 校验认证结果允许访问当前工作空间和目标资源，且 header 中的工作空间（若保留兼容字段）与认证结果一致。
4. 在这一个事务内完成所有业务读写、审计写入和幂等判断；提交或回滚后才将连接还给池。

禁止连接级永久 `SET app.workspace_id`、将调用方写入的 Workspace GUC 当作授权、跨事务复用租户 context，或在认证函数建立 proof 之前访问业务表。测试必须覆盖连接池复用，证明上一个请求的租户 proof 不会泄漏到下一个请求。

凭据的前置验证本身需要在尚未建立租户 context 时查询。该查询只能通过单独的 `auth` 投影/最小 `SECURITY DEFINER` 函数完成。冻结草案 [001](../database/001-租户与凭据.sql) 的 `auth.authenticate_api_credential(key_id, presented_verifier)` 是**仅授予 `ba_runtime`** 的运行时路径：它按不可猜测的 key ID 与 verifier 查询，返回字段仅限 `workspace_id`、`credential_id`、`credential_kind`，同时建立 `<workspace>:<credential>:<txid>:<signature>` proof；scope、成员资格和资源 grant 在认证成功后通过 RLS 查询。`ba_control_executor` 不获该函数执行权，也不能以 API key 模拟管理身份。

控制面使用不同的可信身份边界。经过 IdP/SAML/本地管理登录验证的管理身份网关，才可以由独立的 `ba_management_attestation_issuer` 角色调用受限生命周期函数，写入短期 `control_session_attestations`；记录绑定 `workspace_id`、管理 `principal_id`、数据库 `session_user`、issuer/主体哈希、仅在服务端通道传递的派生 verifier、签发时间、到期时间和撤销状态，不保存原始 IdP token、浏览器 cookie 或会话内容。该 issuer 角色没有租户表 DML；`ba_control_executor` 对该表也没有 `SELECT/INSERT/UPDATE/DELETE` 权限，不能签发、延长或撤销 attestation。

控制请求在同一事务、任何业务表读取前，只能调用 `auth.establish_control_workspace_context(attestation_id, presented_verifier)`。它**不接收 workspace 参数**：从仍有效、未撤销且 `session_user` 匹配的 attestation 导出 workspace 与 principal，随后以当前 `workspace_members` 中的 `admin/developer` 成员资格复验并锁定该行；成功后才写入 `control:<workspace>:<attestation>:<principal>:<txid>:<signature>`。`app.current_workspace_id()` 在每次 RLS 求值重新验证这六部分签名、attestation 的过期/撤销状态、`session_user` 和当前成员资格。因此改写 `Workspace-Id`、`app.workspace_id`、attestation 的 workspace/principal、在另一 DB session 使用旧 context，或在提交后重用旧 context 都不能取得租户上下文；仍有效的 attestation 只能由可信网关重新建立一个新的本事务 context。函数不能成为读取任意业务表或绕过 RLS 的通用入口，必须固定 `search_path` 并最小化返回字段。

内部 admission/metering/finalizer/reconciliation 不得调用 `authenticate_api_credential()` 或使用任意外部 `service_api|publish|webhook|mcp|permission_callback` 凭据建立阶段上下文。只有独立 `ba_internal_service_attestation_issuer` 可签发最长 15 分钟、绑定 `workspace_id + session_user + service_phase` 的 `internal_service_attestations`；阶段 executor 只能以 `auth.establish_internal_service_workspace_context(attestation_id, verifier, expected_phase)` 建立 `service:<workspace>:<attestation>:<phase>:<txid>:<signature>`。helper 每次重新校验到期/撤销、绑定 session user、phase 和该 executor 的精确角色成员资格；错 phase、跨连接、跨事务或外部 credential 复用均 fail closed。该 context 不产生公开 API principal，不能调用 principal-scoped Run 端点。

### 3. 异步、缓存、检索和对象存储也携带同一租户边界

- BullMQ job 必须携带不可变 `workspace_id`、资源/运行 ID、授权决策 ID 或内部服务身份 ID；Worker 在执行前校验持久化记录和 payload 的 workspace 一致，然后在新事务中使用与当前阶段一致的短时 internal service attestation 建立签名 tenant context，不能只执行 `SET LOCAL`或使用外部 API credential。重试、去重键、死信和运行检查点均包含 `workspace_id`。
- Redis key、限流桶、幂等键和分布式锁以 `workspace_id` 作为首段命名空间；禁止只以资源 UUID 或会话 ID 作为跨租户键。
- MinIO 对象路径采用 `workspace_id/<resource>/...`，签名 URL 限定对象、方法、过期时间和租户前缀。对象元数据回写数据库时仍受 RLS 约束。
- pgvector、OpenSearch 和 ClickHouse 查询必须接收并强制租户过滤；不能仅依赖调用方先选中了某个知识库。索引、导出和观测查询同样不能跨租户混合。
- 运行时服务间调用传递经过签名/认证的租户上下文或内部服务身份，不传递可被客户端伪造的裸 `workspace_id` 作为授权依据。

### 4. 凭据按用途分离，最小 scope 与资源授权并存

不再使用 Workspace 级万能 `access_key`。保留 `Access-Key + Workspace-Id` 只是兼容请求外形；其中的 key 是具有类型、scope、资源授权和过期时间的凭据。

| 凭据类别 | 使用者与传递方式 | 最小权限与硬限制 |
|---|---|---|
| 管理身份 | 人类登录会话、OIDC/SAML 或本地管理会话，经可信网关换成短期 DB attestation | 仅控制面；成员、发布、凭据管理由角色和二次确认控制；绑定 principal、workspace、`session_user`、到期/撤销和当前成员角色；不能作为外部 API Key |
| 服务 API 凭据 | 服务端集成经 `Access-Key`/标准 Authorization header | workspace 作用域 + 精确 API scopes + 可选 Agent/Flow allowlist；不允许浏览器持有 |
| 发布凭据 | 宿主后端用于最终用户 browser-session exchange | 仅指向一个稳定 Agent Deployment，只允许 `browser-session:exchange`；不能直接调用 Agent/Flow/A2A、创建/管理/枚举工作空间资源，也不得下发到浏览器 |
| 浏览器会话令牌 | 宿主后端经 exchange 为已验证最终用户取得、再通过自身认证通道交给 Web SDK 的短期 Bearer token | 绑定 `audience`、workspace、稳定 Deployment、channel、origin、平台 `principal_id`、到期时间和 `session_epoch`；仅可调用该 Deployment、访问该 principal 的会话/Run，不可用作服务 API Key |
| Webhook 凭据 | 入站回调的签名 header、mTLS 或等价非 URL 认证 | 仅触发一个 endpoint/已发布版本；带时间戳、nonce 或事件 ID 的防重放；G0/G1 不存在 query/path credential；不可访问管理/API/MCP |
| MCP 凭据 | MCP client 的 Authorization header 或安全配置存储 | 仅一个 MCP service 与工具 allowlist；secure Profile 禁止将秘密拼进 URL |
| 出站集成密钥 | 自定义插件、工作流鉴权、权限 SPI 调用 | 存于服务端 secret reference，按目标系统与操作 scope 隔离；永不返回浏览器、Flow 日志或模型上下文 |

权限 SPI 的出站认证使用专用回调凭据（请求签名、mTLS 或专用 token），不能复用服务 API 凭据。插件 `auth_config` 不得保存原始 token；数据模型只保存 `secret_ref`、认证类型、目标和过期元数据，实际秘密由部署方可用的加密密钥/秘密存储保护。

`api_credentials.credential_kind` 的 G0/G1 数据库枚举精确为 `service_api | publish | webhook | mcp | permission_callback`。管理身份不是该表的凭据类型，只经独立可信管理会话 attestation 路径建立。

`deployment_publish`、`agent_invoke`、`flow_invoke` 及 Run read/cancel/resume/events 只属于 `CredentialOperationPolicyV1` 的 operation purpose：它们由当前 OpenAPI operation 确定，不持久化为凭据列、profile 表或新的 epoch source，也不单独赋予权限。授权决策必须在同一准入事务联合回读：（1）`api_credentials` 的 kind/status/time window/epoch；（2）operation 要求的 `api_credential_scopes`；（3）对应 Agent 或 Flow 稳定 Deployment 的类型化 entry grant 及其 epoch；（4）目标基数。对 Run read/cancel/resume/events，目标不由请求重选，而是回读原 Run 已固定的 target kind/Deployment 并检查同一类型 grant 仍有效。任一事实缺失、多目标或 epoch 失配都 fail closed。

浏览器 SDK 不能再把永久 Workspace Key 或稳定 publish credential 打包到页面。G1 固定采用宿主后端 exchange：宿主后端先认证最终用户，再以仅服务端保存的 Deployment publish credential 和由预配置 issuer 签名、带 audience/nonce/短有效期的 `subject_assertion` 调用 `POST /v1/oapi/browser/sessions/exchange`。平台验证两项凭据及 exact origin allowlist，从 assertion 的 issuer/subject 映射或创建平台 `principal_id`，返回短期 Bearer token；宿主后端只能通过自己的已认证 bootstrap 响应把 token 交给该用户。exchange 请求不得直接提交或选择 `principal_id`，未验证的 `user.id`、昵称、DOM 配置和 query 参数都不是身份依据。

G1 的 Origin 规则在 exchange 与每次请求共用同一个服务端 canonicalizer：只接受单个绝对 `https` origin；用标准 URL 解析器取 `scheme + IDNA ASCII lowercase host + normalized port`，省略 HTTPS 默认端口 443，并拒绝 userinfo、path（`/` 根路径除外）、query、fragment、wildcard、`null`、缺失、多值和解析失败。`allowed_origins`、assertion 内声明的 origin、session.origin 和请求时 Origin 全部保存/比较该 canonical 文本，只允许完全相等，不做 suffix、regex 或子域推断。

browser session 固定绑定 `workspace_id + deployment_id + channel + principal_id + canonical_origin + audience + expires_at + session_epoch`。每次 Chat、Conversation、Run read/cancel/resume 与 events-session 请求都必须在建立 transaction principal/访问业务表**之前**从服务器实际收到的唯一 `Origin` header 重新 canonicalize，并与 session 绑定值精确匹配；不信任 query/body/assertion 重复声明或 `X-Forwarded-Origin`，CORS 响应头也不是授权。反向代理必须原样传递该 header；丢失或改写时请求 fail-closed。纯服务间 credential 不适用浏览器 Origin 绑定，不得伪造 Origin 来进入 browser-session 路径。每次请求还要复验 session/Deployment 状态与 epoch；header/body 中的 Workspace、Agent selector 或 `user.id` 只能做一致性检查，不能改变主体或越过 Deployment。G1 不开放匿名 public Agent，也不允许 browser session 使用未显式授予该 principal 的 delegated connector；匿名 session、公共限流和匿名 delegated 能力后移到 G2。origin allowlist 只是附加约束，不能替代 subject assertion 或 session 验证。

### 5. 凭据只存验证材料，必须可轮换、撤销与审计

凭据元数据采用独立租户表，最低包含：

```text
credentials(
  id, workspace_id, kind, key_hint, verifier_hmac,
  status, issued_at, expires_at, last_used_at, revoked_at, rotation_group, authorization_epoch
)
control_session_attestations(
  id, workspace_id, principal_id, bound_session_user,
  issuer, issuer_subject_hash, attestation_verifier_hmac,
  issued_at, expires_at, revoked_at, revoked_reason
)
browser_subject_assertion_uses(
  id, workspace_id, issuer_config_id, assertion_nonce_hash, subject_hash, audience,
  assertion_issued_at, assertion_expires_at, consumed_at,
  unique(workspace_id, issuer_config_id, assertion_nonce_hash)
)
browser_sessions(
  id, workspace_id, deployment_id, principal_id, channel, origin, audience,
  assertion_use_id, session_verifier_hmac, session_epoch, issued_at, expires_at, revoked_at,
  unique(workspace_id, assertion_use_id)
)
credential_scopes(credential_id, workspace_id, scope)
published_release_visibility(workspace_id, published_resource_version_id, visibility, authorization_epoch)
agent_deployment_entry_grants(credential_id, workspace_id, agent_deployment_id, channel, scope, authorization_epoch)
flow_deployment_entry_grants(credential_id, workspace_id, flow_deployment_id, channel, scope, authorization_epoch)
internal_system_release_grants(credential_id, workspace_id, published_resource_version_id, authorization_epoch)
knowledge_index_generation_grants(credential_id, workspace_id, knowledge_index_generation_id, authorization_epoch)
database_operation_release_grants(credential_id, workspace_id, database_operation_release_id, authorization_epoch)
plugin_tool_release_grants(credential_id, workspace_id, plugin_tool_release_id, authorization_epoch)
skill_pack_release_grants(credential_id, workspace_id, skill_pack_release_id, authorization_epoch)
a2a_agent_release_grants(credential_id, workspace_id, a2a_agent_release_id, authorization_epoch)
authorization_decision_epoch_sources(decision_id, workspace_id, source_kind, source_id, source_subkey, observed_epoch)
secret_refs(id, workspace_id, provider, opaque_locator, purpose, rotation_due_at)
```

公开 Agent/Flow 入口只经稳定 Deployment 的 `agent_deployment_entry_grants` / `flow_deployment_entry_grants`；两者是 G0-05 各自的类型化唯一事实源，不能用通用 release grant 替代。`api_credential_release_grants` 基线物理表只可表达 `service_api -> SYSTEM` 内部授权；preview/test 若需直连未激活 revision，必须是未来独立 management-attested schema，不得复用公开 credential。知识、数据库、Skill、A2A 和租户插件等依赖资源各自使用类型化 release/grant 表。不得恢复 `credential_resource_grants(resource_type, resource_id, release_id)` 或 `resource_visibility` 这类多态 ID 表，也不得以 JSON 允许列表替代这些复合关系。

`opaque_locator` 只是 secret provider 内部不透明、不可解释的定位符，不是密文、不承诺包含加密材料，更不能放原始 secret；只有部署侧 provider adapter 可以把它解析为一次性 handle。

`verifier_hmac` 是对高熵原始秘密做带服务端 pepper 的 HMAC 验证材料；原始秘密只在创建或轮换成功时显示一次，之后不可读回。它虽不是原始值，但在**数据库权限边界必须按 bearer-equivalent secret** 处理：`ba_runtime`、`ba_control_executor`、admission/metering/finalizer/reconciliation executors 和普通应用角色显式撤销 `api_credentials` 整表 SELECT，只对必要的非 verifier 列授予列级 SELECT；它们也不能读取私有 `auth.credential_auth_index`。只有 `ba_auth_owner` 所有的认证函数可读该投影，且只返回 workspace/credential/kind。认证先按不可猜测 key ID 定位候选，再用私有、固定 32-byte、遍历全部字节的 `auth.constant_time_equal_32` 比较 verifier；普通 `bytea/text =` 不是可接受替代。presented verifier 必须以 binary bind 参数通过受信服务端通道传入并标为 never-log；生产 gate 必须证明 PostgreSQL `log_parameter_max_length=0`、`log_parameter_max_length_on_error=0`，连接池/APM/错误记录器也不采集参数。任一层无法证明时认证部署 fail-closed。browser exchange 必须在同一事务先以 issuer + nonce hash 原子占用一条 `browser_subject_assertion_uses`，再创建唯一关联 session；重复 assertion 即使尚未过期也拒绝，失败事务不留下半消费记录。数据库、迁移、审计、任务、SSE、OpenTelemetry、异常和支持导出不得包含原始秘密、完整 Authorization header、query secret、assertion 原文或可重放签名。

每个凭据有独立 ID、状态 `active|overlap|revoked|expired`和单向生命周期。轮换必须创建新凭据；旧凭据进入 `overlap` 时必须有服务端生成的同一 `rotation_group`和不晚于 24 小时的绝对 `expires_at`，进入后不得更换 group、延期或回到 active。`revoked|expired` 不得回活，终态生命周期元数据不可改写；认证必须拒绝无 `rotation_group` 或无期限的 overlap。紧急撤销立即生效并使授权决策缓存失效。凭据、scope/grant、release visibility、策略或资源 release 的授权相关变更必须经受限 `SECURITY DEFINER` mutation function/trigger，在同一租户事务单调递增 source 与 Workspace `authorization_epoch`、追加 durable cache invalidation；source 行不得以 DELETE 静默移除。决策缓存以 `authorization_decision_epoch_sources` 的多源 epoch 集合为键或主动失效，尚未开始的调用在同一 RLS 事务比较该 Decision 保存的同一权威 source 集。为兼容“重新生成后旧 Key 立即失效”的外形，可提供显式 `immediate_revoke` 轮换选项，但它不是默认轮换流程。

所有创建、查看 key hint、轮换、撤销、scope/grant 修改及异常使用都写不可篡改审计事件，记录操作者、凭据 ID、目的、来源和时间，不记录秘密本身。

### 6. G0/G1 完全禁止 URL 中的秘密

G0/G1 secure Profile 中，服务 API、浏览器 SDK、Webhook、权限 SPI 和 MCP 一律禁止在 URL query、path、fragment、配置截图或日志中携带可认证秘密。MCP 使用标准 Authorization header/安全配置；Webhook 使用来源平台签名、mTLS 或可设置 header 的专用签名。当前 schema、OpenAPI、credential kind/config 和 ingress router 不存在 URL credential、legacy MCP 或启用开关；遇到 query/path secret 必须在认证前拒绝，不能靠日志脱敏后继续执行。

未来若真实不可改造渠道必须支持 URL credential，它只能先形成**独立 sealed safety envelope**：新 ADR/schema version、独立凭据类型与入口、不可复用的专用 secret、最大 TTL/来源约束、代理与 Referer 防泄漏、双人风险审批、迁移/弃用期限、独立审计和可执行 acceptance gate。该 envelope 未迁移并过门前只是研究材料，不能由配置、管理员开关、隐藏字段或旧数据激活，也不得回填进 G0/G1 表。

## 替代方案

### 方案 A：只在顶级表保存 `workspace_id`，应用层沿父表校验

拒绝。子表查询、异步任务、日志、搜索和多态引用很容易漏掉 join 条件；数据库无法证明跨租户引用非法，P0 的越权测试也无法覆盖所有未来查询。

### 方案 B：在连接池上执行永久 `SET app.workspace_id`

拒绝。连接复用和异常路径会使上一个请求的租户上下文泄漏给下一个请求。事务级 `SET LOCAL`/ `set_config(..., true)` 才能在提交、回滚后自动清除。

### 方案 C：继续使用一个 Workspace 级明文 API Key

拒绝。它无法表达最小权限和资源授权，也使 SDK、Webhook、MCP、SPI 任一泄露扩大为整个工作空间泄露，且无法安全地轮换不同集成。

### 方案 D：在 G0/G1 保留 URL 兼容开关

拒绝。query/path secret 会穿过代理、浏览器历史、Referer、分析与支持链路；日志脱敏不能撤销已经扩大的传递面。真实互操作需求只能进入未来独立 sealed safety envelope，不能成为当前 secure baseline 的 dormant bypass。

## 后果

正面后果：

- RLS、复合外键和事务上下文形成三层可验证的租户边界；
- 凭据泄露的爆炸半径从“整个工作空间”缩小到特定资源和 scope；
- SDK、Webhook、MCP、插件和 SPI 有了清晰、不互相复用的凭据责任；
- Worker、缓存、检索与对象存储被纳入隔离模型，而不是只保护主数据库表。

成本与限制：

- 所有表、关联、查询、索引、队列 payload 和缓存键需要补齐 `workspace_id`，迁移量较大；
- 认证前置查询、租户事务封装、RLS 测试和 secret reference 增加 P0 实现工作；
- 旧 SDK 的永久 key 配置必须迁移到发布标识/短期 token 流程；
- 部分只能使用 URL 的第三方集成将得到更严格的能力和运维要求。

## 安全与兼容边界

- `Workspace-Id` 是声明值而非权限证明；它必须与认证后的凭据/成员所属工作空间相同。
- `FORCE ROW LEVEL SECURITY` 不阻止超级用户或 `BYPASSRLS` 角色；生产运行账号不得持有这些权限，维护账号的使用须走受控运维流程。
- RLS 不能替代对象存储、搜索、缓存和日志隔离；上述系统分别执行租户过滤/命名空间约束。
- 包含用户输入、模型输出、工具结果和业务秘密的运行记录不得作为凭据存储或传递渠道。工具/插件只接收其被授予的 `secret_ref` 解密结果，且不会回写到 Flow 变量。
- 兼容旧路径和字段名不允许把旧的万能 `access_key` 继续暴露给浏览器、URL、MCP 配置或权限 SPI。

## 验收证据

实现 P0/P1 前必须给出以下可复现证据：

1. 迁移审计：列出每张租户表的 `workspace_id not null`、RLS 启用/强制状态、policy、复合外键、索引和全局表豁免理由；不存在未解释的间接租户表。
2. 使用普通应用角色的 Postgres 集成测试：没有有效签名 `app.tenant_context` 时读写零行；认证为 A 的 context 不能读写 B；表所有者受 `FORCE RLS` 约束；跨租户复合 FK 插入失败。
3. 连接池复用测试：事务 A 认证为 workspace A 后提交/回滚并释放连接，下一事务在重新认证前或认证为 B 后均无法继承 A 的数据。
4. HTTP、SSE、Worker、定时任务、重试和死信的端到端测试：篡改 payload 中的 `workspace_id` 或资源 ID 被拒绝，且 run/credits/logs 不跨租户写入。
5. Redis、MinIO、pgvector/OpenSearch、ClickHouse 的集成测试：故意使用相同资源/会话标识时仍不能跨租户命中、读取、导出或复用缓存。
6. 凭据安全测试：数据库、审计、SSE、OTel 和错误日志中找不到新生成的原始秘密；以 `ba_runtime`、`ba_control_executor`、admission/metering/finalizer/reconciliation executor 和普通 app role 执行 `SELECT * FROM api_credentials` 或直读 `secret_verifier_hmac` 失败，只查询显式安全列成功，私有 auth projection 直读失败，认证函数不返回 verifier。部署读回 `log_parameter_max_length=0`、`log_parameter_max_length_on_error=0` 及 pooler/APM never-log 配置；用唯一 canary verifier 分别触发成功、错误长度、错误首字节、错误末字节和 SQL 异常后扫描 DB/pooler/APM/error/support export 均为零命中。部署函数定义必须仍调用 `auth.constant_time_equal_32`，普通 equality 替换被 schema test 拒绝；相同样本量下首/末字节错误与正确比较的延迟分布不得出现超过预先冻结阈值的稳定可区分信号。不同 workspace、scope、类型化资源 grant、过期或撤销状态均被正确拒绝；无法由 registry/类型表复合 FK 证明的多态资源 grant 无法写入。数据库 catalog 还必须证明没有 credential-purpose/profile 列或表；OpenAPI 每个 `x-service-credential-policy` 都能映射到 kind + scope + 类型化 entry grant + target cardinality，并对 publish 直调、Agent/Flow grant 混用、多目标与原 Run 目标替换执行 fail-closed fixture。
7. 兼容契约测试：携带受限服务 API 凭据的 `Access-Key + Workspace-Id` 仍能访问获授权的既有 REST 路径；header workspace 与凭据 workspace 不同则拒绝。
8. 浏览器、Webhook 与 MCP 测试：浏览器包无永久 key/publish credential；只有服务端 publish credential 加有效、未重放的 subject assertion 才能 exchange；伪造 `user.id`、直接提交 `principal_id`、错误 issuer/audience/nonce/origin/Deployment、过期或旧 `session_epoch` 均被拒绝。Origin fixture 覆盖 host 大小写/IDNA/默认端口的 canonical 等价，以及 HTTP、非默认端口错配、path/query/fragment/userinfo、wildcard/`null`/缺失/多值/恶意 `X-Forwarded-Origin` 的 fail-closed；Chat/Conversation/Run read/cancel/resume/events-session 每条 browser-token 路径都在 DB context 前执行该精确比较。两个最终用户的 Conversation/Run/幂等记录不可互读，且缺少 delegated grant 不回退到发布者身份。Webhook 签名可验证且重放被拒绝；任意 URL/path secret、legacy MCP 标记或未知 compatibility 字段在认证前失败，数据库 catalog 证明没有可激活的 fallback 列、表、枚举或 source kind。
9. 控制面 context 集成测试：`ba_control_executor` 不能执行 `authenticate_api_credential`，也不能直接读写 `control_session_attestations`；经可信 issuer 签发且 `session_user`、principal、workspace、`admin/developer` 成员角色均匹配的 attestation 才能在同一事务建立 context。过期/撤销 attestation、错误 verifier、错误 `session_user`、被移除或降级的成员、伪造/改写 workspace 或 principal、跨 transaction/连接复用**旧 context**均返回无 context 且 RLS 零行；仍有效 attestation 只能由可信网关重新建立新的 context。直接 DML、attestation ID 再签发和未受信任 issuer 签发均失败。
10. 内部阶段 context 集成测试：admission/metering/finalizer/reconciliation executors 不能执行 `authenticate_api_credential`或直读 attestation/verifier 表；只有绑定相同 `workspace_id + session_user + service_phase`、最长 15 分钟且未撤销的内部 attestation 能建立本事务 context。任意外部 credential、wrong-phase、错误 executor role、跨连接/事务复用均返回无 context 且 RLS 零行；内部 context 不产生可读取 principal-scoped Run 的 principal。
