# ADR-001：兼容性与安全默认值

- 状态：已接受（文档级架构决策；尚未实现，真实证据待 G0）
- 日期：2026-08-24
- 决策范围：外部调用、渠道、权限 SPI、资源发布与 Flow 运行时的授权语义
- 关联：[架构分析](../01-架构分析-betteryeah.md)、[技术架构](../04-技术架构.md)、[数据模型](../05-数据模型.md)、[API 契约](../06-API契约.md)、[实施计划](../07-实施计划.md)

## 背景

本项目的证据基线要求复刻资源命名、API 路径、请求头和 task 事件流；外部 API 使用 `Access-Key + Workspace-Id`，并已规划 Agent、Flow、Webhook、MCP、Web SDK 和多个渠道入口。

竞品行为同时包含一个不能作为私有化产品默认行为的语义：当权限身份未设置、设置不全，或 SPI 的 `allow` 未提供时，权限管控不生效（fail-open）。现有设计也将 `strict_permission_mode` 设为默认关闭。对于无法稳定提供 `user_id` 的渠道，这会让原本受限的知识库、插件或工作流被静默放行。

私有化交付意味着部署方将把内部数据、模型凭据和业务入口置于同一信任边界内。API 外形兼容不等于必须将不安全的授权失败语义作为默认值；否则一次错误配置、SPI 超时或渠道身份缺失即可扩大为数据泄露。

## 决策

### 1. 使用显式的兼容性 Profile，默认采用安全语义

授权行为由工作空间级 `compatibility_profile` 决定，取值如下：

| Profile | 默认 | 权限身份、SPI 或策略不完整 | 适用场景 |
|---|---:|---|---|
| `secure` | 是 | 对受保护资源拒绝（fail-closed） | 所有新建私有化工作空间 |
| `betteryeah_legacy` | 否；G0/G1 不可激活 | 未来只可在独立 compatibility envelope、迁移与验收门落地后，按本文受限范围处理已成功但不完整的业务权限信息 | 明确需要行为回归兼容的受控迁移 |

新建工作空间必须显式写入 `secure`。不得再以 `strict_permission_mode=false` 作为默认安全策略；该布尔字段不再是运行时决策源。

**G0/G1 交付只实现 `secure`。** 数据库可保留“待评估的遗留导入意图”，但不得把 Workspace 切到可执行的 `betteryeah_legacy`，也不得因此允许 `floating_latest`、可变依赖、凭据 fallback 或未 seal 的 capability closure。未来兼容实现必须以新的 schema/migration 引入不可变 `CompatibilityVersionEnvelopeRelease`，固定允许版本集合、operation/schema、egress、数据分类、副作用上限、审批与 epoch；新增版本必须重新审批并重新 seal。

当前仓库尚未实施生产迁移，因此不进行“`false` 自动迁入 legacy”的静默映射。未来导入旧配置时，迁移工具必须把未选择的值标成“待管理员确认”，默认落入 `secure`。若仍需保留 `strict_permission_mode` 作为兼容设置 UI 或旧配置导入字段，它只能映射到 Profile 并留下审计记录：

- `true` 映射为 `secure`；
- `false` 在 G0/G1 只能映射为“待管理员评估”的导入状态；未来兼容门完成后才可由管理员明确确认并映射为可执行的 `betteryeah_legacy`；
- 请求不得用任意 header、body 参数或 Flow 变量覆盖 Profile。

### 2. 授权采用统一的 fail-closed 判定链

每个外部入口必须在执行模型、工具、检索、数据访问或写审计日志之前完成同一条授权链：

```text
认证凭据 → 确认 workspace 与凭据 scope → 解析发布资源/版本
→ 解析调用者身份 → 权限 SPI（如已配置）→ 资源可见性与 allow 判定
→ 生成不可变 AuthorizationDecision → 执行
```

`AuthorizationDecision` 至少携带 `workspace_id`、调用者种类、资源类型/ID/发布版本、允许的工具与知识库范围、Profile、判定原因码和过期时间。Agent、Flow、MCP、Webhook、SDK、渠道适配器、异步续跑均只能消费该决策，不能自行重写或跳过权限检查。

在 `secure` Profile 下：

- 仅明确标记为 `public` 的已发布资源可在没有可验证身份时调用；发布前必须声明资源可见性，默认不是 public。
- 受保护资源的 `user_type`、`user_id` 缺失或格式无效、SPI 超时/网络错误/响应不合法、请求资源未在结果中、`allow` 缺失或未含该资源时，一律拒绝。
- SPI 未配置不等同于“全部资源公开”。未配置 SPI 时，只有资源发布策略明确允许的访问可通过；Studio 内访问仍由成员角色和资源权限控制。
- 拒绝响应不得区分“资源不存在”和“无权限”，不得返回知识库片段、工具名、模型输出或部分 Flow 节点结果。

在未来 compatibility envelope 已实现且通过独立验收门后，`betteryeah_legacy` Profile 才可保留兼容所需的 `allow` 缺失、身份未配置或配置不全时不额外裁剪资源的语义；但它不是绕过以下硬性控制的手段：

- 无法提供可验证 `user_id` 的渠道，不得绑定任何非 `public` 数据、知识库、数据库、插件或 Flow；配置期校验和发布期校验均必须拦截。
- 仍需通过凭据认证、工作空间隔离、资源发布状态、凭据 scope、限流、审计和租户 RLS。
- SPI 超时、网络错误、签名失败或响应畸形不得被当作有效授权；legacy 仅复刻“已成功获得但不完整的业务权限信息”语义。若需要复刻更宽松的超时行为，必须另立 ADR。

这意味着“完整复刻不安全的对外暴露组合”不属于兼容承诺；这是有意的私有化安全边界。

### 2.1 G0/G1 权限 SPI 的有界失败策略

G0/G1 的权限 SPI 策略属于不可变 Deployment revision，而不是运行时可任意调大的环境变量。默认单次调用硬超时为 `2s`，同一次 admission 内不自动重试；客户可以在新的 revision 中降低超时，但提高上限必须经过契约评审。成功的 allow decision 最多缓存 `30s`，deny decision 最多缓存 `5s`，且两者都不得超过 credential、session、policy 或回调返回值自身的过期时间。任何 authority epoch 变化立即使缓存失效；超时、断路、签名错误、畸形响应和缓存不一致都不能读取 stale allow 或降级为放行。

运行指标至少区分 success、deny、timeout、transport failure、invalid response 与 cache hit/miss；面向企业调用方的错误只暴露稳定 reason code、trace ID 和可重试建议，不返回内部资源是否存在、策略正文或回调响应。重试只允许由上游对整个尚未产生副作用的 admission 使用新的 transport request 发起，并仍受原幂等键约束。

### 3. 兼容的是外部契约，不是默认风险

以下接口外形可保持兼容：既有 REST 路径、`Access-Key` 与 `Workspace-Id` 请求头、`task` 响应字段、SSE 的事件顺序，以及权限 SPI 的请求/响应字段。安全 Profile 改变的是服务器如何判定未授权请求，而不是让客户端猜测新的接口形状。

兼容 Profile 的启用条件：

1. 仅工作空间 `admin` 能操作，且需要二次确认和风险说明；
2. 变更记录必须包含操作者、时间、旧/新 Profile、理由、受影响的发布资源和渠道；
3. 启用前执行资源暴露扫描：列出非 public 资源、无 `user_id` 渠道、SPI 健康状态和不合规绑定；发现不合规项则拒绝启用；
4. Profile 变更后立即使旧的授权决策、浏览器会话令牌和运行时权限缓存失效；
5. UI、CLI 和 API 都必须展示当前 Profile，不能只隐藏在数据库字段中。

### 4. 把发布可见性和权限边界前移到编译与配置阶段

每个可被外部调用的 Agent、Flow、MCP 服务、A2A 服务及其发布版本必须声明可见性（至少 `private`、`authenticated`、`public`）和允许入口。资源绑定必须记录所依赖的知识库、数据库、插件和子 Flow 的最小访问范围。

可见性只定义“哪些主体类别有资格继续授权”，从不单独产生 allow；endpoint scope、类型化 entry grant、Deployment/channel、依赖资源 grant、数据分类、预算和策略仍须全部通过：

| 可见性 | 冻结语义 | G1 行为 |
|---|---|---|
| `private` | 不允许匿名或仅凭“已登录”获得访问；只允许 Workspace 控制面成员，或被类型化 entry grant 精确点名的 service/browser principal。 | 支持；默认值。 |
| `authenticated` | 允许已验证且绑定 Deployment/channel 的非匿名 principal 进入后续授权；服务凭据仍需 kind + scope + typed grant，browser 仍需 host-backed exchange session。 | 支持。 |
| `public` | 仅表示未来匿名主体可以进入后续限流、abuse-control 与 dependency-public-safety 检查，不表示依赖资源自动公开。 | G1 不开放匿名，因此按 `authenticated` 的身份下界执行；匿名入口在 G2 独立 gate 前 fail-closed。 |

所有资源类型默认 `private`。任何顶层资源提升可见性时，publisher 必须证明完整 capability closure 的每项依赖不比顶层更窄，或存在对该主体有效的显式 typed grant；无法证明时发布失败。可见性收窄或撤销递增权威 epoch，不能由请求字段覆盖。

发布/编译阶段必须拒绝以下组合：

- `public` 资源引用未显式公开或未获匿名访问授权的知识库、数据库、插件、子 Flow；
- 无 `user_id` 渠道引用非 public 资源；
- 安全 Profile 下，以“SPI 空响应”“缺少 `allow`”作为访问控制配置；
- 任何入口将请求中的用户、工作空间、资源 ID 或 Profile 当作可信授权结论。

运行时仍须重新检查，因为配置检查无法替代凭据撤销、资源下线、成员变更和 SPI 结果变化。

## 替代方案

### 方案 A：完全照抄 fail-open，默认关闭严格模式

拒绝。它满足最表面的行为相似度，却将身份缺失、SPI 故障和渠道差异转化为默认放行，和私有化优先的交付目标冲突。

### 方案 B：只保留 `strict_permission_mode` 布尔开关，默认关闭

拒绝。布尔值无法表达“兼容模式是显式风险例外”，也无法承载启用前扫描、审计、渠道约束和缓存失效等治理要求；默认值仍会把风险带回新工作空间。

### 方案 C：取消所有兼容语义，统一强制严格模式

不采用。它更安全，但会破坏部分已有 SDK、渠道和 SPI 部署的预期，增加迁移阻力。显式的 `betteryeah_legacy` Profile 提供了有限、可审计的过渡路径。

## 后果

正面后果：

- 新部署不会因默认值或 SPI 故障意外扩大数据可见范围；
- 1:1 兼容范围变得可陈述、可测试，且不会把不安全语义伪装成正常配置；
- 所有入口共享 `AuthorizationDecision`，可减少 SDK、Webhook、MCP 与 Worker 间的权限漂移。

成本与限制：

- 需要新增发布可见性、兼容 Profile、决策缓存失效和配置扫描；
- 部分无身份渠道只能服务 public 内容，客户需要改造渠道身份映射或调整发布范围；
- 同一请求在 secure 与 legacy Profile 下可能得到不同授权结果，测试和文档必须显式覆盖两种模式；
- 现有文档中关于 `strict_permission_mode default false` 的描述需由后续架构、数据模型和 API 契约更新替代。

## 安全与兼容边界

- 兼容 Profile 不降低凭据强度、租户隔离、RLS、工具 sandbox、出网控制、审计或积分并发保护要求。
- 权限 SPI 的 `Access-Key` 不能复用为浏览器、Webhook、MCP 或管理凭据；凭据分类、轮换和 URL 限制由 ADR-003 定义。
- 授权日志只记录判定原因、资源标识、Profile、追踪 ID 和最小必要身份摘要；不得记录原始密钥、SPI 返回中的敏感属性、Prompt 或检索正文。
- 服务端错误、拒绝或超时均不得产生“已经开始执行但看似未授权”的副作用；对于已进入异步队列的任务，Worker 必须在执行前重新验证不可变决策及其有效期。

## 验收证据

实现 G0/G1 secure baseline 时先满足 1～4、6；未来 compatibility envelope 启用前再满足第 5 项和对应 legacy 分支，不能用未来测试反向阻塞 G0-01：

1. 新建工作空间的数据库读回与 API 响应均为 `secure`，且请求无法覆盖 Profile。
2. 安全 Profile 的矩阵集成测试：缺少身份、身份不完整、SPI 超时、畸形响应、缺少 `allow`、资源不在 `allow` 中，均返回统一拒绝且没有模型、工具、检索或写入副作用。
3. G0/G1 的回归测试：任何激活 legacy profile、`floating_latest`、凭据 fallback 或未 seal dependency 的尝试都失败。未来若引入 compatibility envelope，再增加允许复刻的完整/不完整 `allow` 契约测试，同时证明无 `user_id` 渠道无法发布非 public 资源。
4. 对 REST、SSE、Webhook、MCP、Web SDK、渠道适配器和异步 Worker 分别执行“同一受保护资源、同一身份缺失”测试，结果一致。
5. **未来 compatibility gate：** Profile 启用/切换的端到端测试证明仅管理员可执行、不合规绑定被阻断、审计完整，且已签发的授权决策和会话令牌失效；G0/G1 catalog 不存在可执行切换路径。
6. 运行日志和追踪导出检查不含原始凭据、完整 SPI 返回、受拒绝资源的正文或部分节点输出。

## 后续决策项与阶段门

下列事项不改变 G0/G1 的 `secure`、pinned、fail-closed 基线，因此不阻塞 G0-01；到达对应阶段仍未形成证据时，该能力保持关闭：

| 后续事项 | 最迟决策点 | 未决时默认行为 |
|---|---|---|
| 遗留客户的 Profile 迁移窗口、风险告知文本和回滚流程 | 独立 compatibility envelope 立项前 | 不提供可执行 legacy Profile，只保留不可执行的导入诊断。 |
| 强身份渠道是否可在 legacy Profile 下访问 authenticated 资源 | 对应渠道/compatibility gate 前 | 拒绝；不得借 G0/G1 的管理开关启用。 |
| 不同客户对 SPI timeout/TTL 的调优 | 新 Deployment revision 发布前 | 使用本文 `2s / 30s / 5s` 上限；只允许收紧，不允许运行时扩张。 |
